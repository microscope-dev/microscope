Node.js, the second managed runtime

Node runs JavaScript on V8. Unlike CPython, V8's frames live on the native stack. Its machine code, though, is written at run time into anonymous memory that no image describes, and its builtins are copied out of the executable at startup. Its own description of its heap, the v8dbg_ postmortem symbols, leaves out the fields that turn a frame into a source line. This plan says how microscope reads all of that exactly from outside the process, how it drives breakpoints and steps through the inspector Node already ships, and how both fit the provider and runtime-model split that Go and Python use. It covers the debugger, values, views, profiling, system calls, the flake, and a testing strategy whose oracles are V8's own accounts of itself.

Summary

It feels like Node. A user runs microscope node -- server.js, breaks in a .js or .ts file, steps across await, and sees values written as console.log writes them, with Node's own frames folded away. On top of that they get what Node's debugger cannot give: native and addon frames, every worker stopped at once, core dumps, profiles, and system calls. What debugging Node feels like walks through a session and the eight changes it made to this plan.

Read the target from outside; let Node's own debugger move it. Stacks, values, expressions, views, profiling, syscall stacks, and core dumps read V8's memory directly, with no code in the target. Breakpoints, steps, exception stops, and assignments go through V8's inspector (the Chrome DevTools Protocol, CDP). Node ships the inspector in every build and can start it in a running process with SIGUSR1. Python needed an injected agent because CPython had no such facility. Node needs none. A launched process gets one preloaded file of about ten lines, which only opens Node's own inspector and waits for microscope, because every --inspect flag changes how node --test runs (F30, F31). microscope learns each inspector's private address from the process's memory, so Node never prints or serves it (F29).

The layout comes from V8's own build, not from guesses. Every official and nixpkgs Node binary exports about 480 v8dbg_ constants (F2). They are read by name. Each Node line renumbers frame types and instance types and moves fields (F3), so no value is ever hard-coded. The symbols leave out what lines and names need, such as the bytecode's position table, ScopeInfo's variable-length layout, and external string data. Those come from V8's Torque compiler, which already generates exact offsets and slice macros for debuggers (class-debug-readers.cc, debug-macros.cc). The flake runs Torque once per supported V8 version, and a checked-in generated file holds the result, exactly as layouts.gen.rs does for CPython. Wherever both sources name a field they must agree, or the binary is refused.

JavaScript frames are native frames with a recorded function. A V8 frame has a frame pointer, a return address, and slots holding its JSFunction and bytecode offset, so the native unwinder walks it. The runtime model only names it. That needs two pieces of groundwork: a pseudo-module that maps V8's remapped copies of its builtins back to the executable's symbols (F7), and a way for a runtime to describe a physical frame whose code is in no image (G2). Optimized frames expand into their inlined functions as inline frames do.

Every LTS line in support, never an old one. microscope supports Node 22, 24, and 26, the three LTS lines in support today, and Node 22 leaves at its end of life in April 2027. From Node 27, each line joins when it enters LTS and leaves at its end of life (Versions). Debian's shared-libnode build is supported from the start too (F28).

The test oracles are V8, twice. A fixture prints what V8's own CallSite API knows at a synchronization point. At inspector stops, CDP's Debugger.paused frames and scopes are a second, independent oracle that microscope's out-of-process reader must match frame by frame. The simulator is not extended (as asked). The CDP controller's interleavings are tested against a scripted inspector instead, which is cheaper and deterministic.

The decisions that most change the work are in Decisions. The smaller ones in Questions were decided on 22 October 2026, three of them against the original recommendation: Node 22 is supported, Debian's libnode build is supported from the start, and nothing is contributed upstream. The research prototypes (a core-dump frame walker in Python, CDP timing clients, and inspector probes) are throwaway and not checked in. Their results are recorded in Findings. A second round of eleven experiments (F16–F26) tested the riskiest parts end to end. The out-of-process reader rendered 75 of 76 values byte-identical to util.inspect. The inspector survives the all-stop. Task lists, the flake's recipes, and the layout translator all worked. They also found the largest gap a Node user will meet first: npm start, node --test, and node --watch run the user's code in a child process that microscope does not follow today (F26).

What debugging Node feels like

The goal: a Node developer who has never heard of V8's internals debugs their program the way they would with node inspect or VS Code's built-in JavaScript debugger. They see the names, lines, and values Node itself would print. They also get what those tools cannot give them: native frames, core dumps, every thread stopped at once, profiles, and system calls, all in one session. Everything in the rest of this plan exists to make that true. V8 shows up only as the reason something cannot be done, written so the user knows what to do next.

The sessions below show the designed behavior; none of it is implemented yet. The output follows the formats microscope already prints for Python and native code.

From Node 27, Node makes one major release a year, in April, and every line becomes LTS after six months as Current. The policy is therefore mechanical. A new line joins each October, which is one flake entry, one regenerated layout, and the conformance and truth suites run on it. Findings

The research read V8 14.6's and 13.6's sources from the Node 26.12.1 and 24.22.1 tarballs, ran V8's Torque compiler on both, and read the OpenTelemetry eBPF profiler's V8 unwinder and llnode. It then ran experiments against nixpkgs' 24.16.0 and the official 24.22.1 and 26.12.1 binaries: a core-dump frame walker, CDP clients timing every operation, and probes of the inspector's startup, worker, and attach paths. Each finding changed the plan. F16 to F26 come from a second round, run on the official 24.22.1 and 26.12.1 builds, with nixpkgs' builds where named. It covered the inspector under the all-stop, binding local names, optimized-code lookup, pause latency and inspector cost, cores, the flake's recipes, task lists, values against util.inspect, and how users launch Node.

F1

Node's release model changes this month

Node 26 is the last line made under the old twice-yearly model. From 27 there is one major a year and every one becomes LTS. So every supported line is an even-numbered line until 26, and every line after it. nixpkgs at the pinned revision has nodejs_22 22.23.1, nodejs_24 24.16.0, and nodejs_26 26.5.0. Node 25 was removed at its end of life.

F2

Every build exports its V8 layout

v8dbg_ symbols are present in the nixpkgs build (480) and the official 24.22.1 (480) and 26.12.1 (477) builds, with 16–17 nodedbg_ symbols beside them. The values are in .data, readable from the file. nixpkgs' 24.16.0 and the official 24.22.1 differ in none of them. A v8dbg_ symbol in .bss means zero, as v8dbg_SmiTag does. On Node 24, though, the nodedbg_ offsets are also in .bss and are non-zero on 26, so on 24 they are set at run time and cannot be read from the file. The plan does not use them where Torque gives the same fact.

F3

Each line renumbers everything

Between V8 13.6 and 14.6, 44 shared non-type constants changed value. Every frame type was renumbered (InterpretedFrame 14→4, TurbofanJSFrame 17→7). Most instance types moved by one to seven. DescriptorArray's header grew from 24 to 32 bytes. 22 symbols disappeared and 19 appeared. A reader that remembers any number from one line misreads the next, so every number is read by name, every time an image loads.

F4

The metadata stops short of source lines

No v8dbg_ symbol gives BytecodeArray's source position table, TrustedByteArray's data, ExternalString's data, SharedFunctionInfo's function data, or ScopeInfo's variable-length slices, which hold function names. The OpenTelemetry unwinder hard-codes these per V8 version, and one of its comments calls its own bytecode-table offset uncertain. V8's Torque compiler emits all of them exactly, for its own debug helper: class-debug-readers.cc (753 fixed-offset fields on 13.6, 736 on 14.6, in the release configuration) and debug-macros.cc, 105 and 109 distinct slice functions in a small subset of C++ (integer add and multiply, field reads, bit fields, and branches). Producing them takes configure (about 13 s) and the run_torque target (3 s), with no V8 build. Of 635 fields both versions name, 52 moved, in 18 classes.

F5

A table change that looks right

The prototype first gave Node's own timers frames lines 649 and 610, where V8's truth said 685 and 618. The cause: V8 14.6 encodes a position table's code offset as an unsigned varint with two flag bits, and 13.6 as a signed one whose sign means "statement". Both decode without error, and both give plausible lines. The encoding is now per-version data in the generated layout, and the conformance suite checks it against each binary's own tables (Testing).

F6

Reading a core works on both lines

From a gcore of each official build, the 230-line prototype used only v8dbg_ symbols and Torque offsets to name the main thread's JavaScript frames. The fixture parked the thread in Atomics.wait after printing its own stack. The prototype's output matched it on every interpreted frame's function, file, and line, through listOnTimeout and processTimers to the EntryFrame, on 24.22.1 and 26.12.1. The Sparkplug frame was named but had no line, because that needs the baseline code's offset table. Node's built-in scripts keep their source as external strings in the executable's read-only data, which the core omits. Those reads go to the module file, as microscope's post-mortem reader already does for file-backed mappings.

F7

Builtins run from copies no image describes

The executable has 2,415 Builtins_ symbols, but return addresses on the stack point into anonymous memory. V8 copies its whole embedded blob (2,182,848 bytes on 26.12.1) next to each code range for short builtin calls. The core held two copies, both byte-identical to the executable's. One return address fell 0xe4 bytes into the copy of Builtins_InterpreterEntryTrampoline. Today microscope's unwinder ends a stack at the first such address. A copy proven identical byte for byte can borrow the executable's symbols, roles, and unwind rules exactly (G1).

F8

Each thread names its isolate

v8::internal::g_current_isolate_ is a static TLS variable in the executable. Reading it at the thread pointer minus the executable's aligned TLS block, plus the symbol's offset, gave the main thread's isolate and zero for libuv's and V8's helper threads. This is how threads map to isolates, and how a helper thread is told apart from a JavaScript thread. A shared libnode would put it in dynamic TLS, which needs glibc's DTV descriptors.

F9

gcore lost a worker's stack, because of glibc's guard pages

The core held only zeros for the worker thread's stack mapping, which also holds its TLS. The cause is gdb, not Node. glibc 2.42 and later install each thread stack's guard with MADV_GUARD_INSTALL inside the stack mapping, so the kernel merges neighbouring stacks into one mapping (45 MiB holding six threads' stacks). Reads of a guard page fail with EIO through both /proc/PID/mem and ptrace. gcore stops at the first failed read and writes nothing more of that mapping. Official binaries run on the host's glibc, here Fedora's 2.43.

The repository already solves this. make_core in scripts/build-test-programs.sh runs fixtures under scripts/stack-guard-mappings, which makes MADV_GUARD_INSTALL fail so that glibc falls back to separate guard mappings, and rejects any “Memory read failed” warning. Under it, every thread's stack and TLS matched the live process. Kernel cores, through coredumpctl, skip guard pages and are complete without it. A core reports 1.9 GB but allocates about 70 MB, and 23 MB after zstd, because 1 GiB of it is two code-range reservations and 0.8 GiB inaccessible reservations, both holes. --abort-on-uncaught-exception dies by SIGTRAP, not SIGABRT. Users' own gcore cores have the same hole, so the core reader reports a thread whose stack bytes are all absent as missing, never as an empty stack.

F11

Stack locals are named only in source

ScopeInfo names only context-allocated variables, the ones closures capture. A stack-allocated local lives in an interpreter register, whose name V8 itself finds by reparsing the function's source (ScopeIterator::TryParseAndRetrieveScopes). So outside an inspector pause no exact reader can name let total in a function no closure captures. Its register is readable, its name is not. At an inspector pause, CDP's scope chain gives the names in V8's allocation order, which binds them to registers (Values).

Stacks

Finding V8 and its isolates

A module is a V8 runtime when its symbol table has the v8dbg_ constants and V8's version symbols. The provider reads them from the module's own bytes, picks the generated layout for the version's major.minor, and checks every field both name. Every exported v8dbg_type_ must equal the layout's instance type too, which catches a build configured differently from the release (F21). The per-build facts of F25 are decoded from their accessors at bind time and checked against the layout's expected instruction shape, or the binary is refused by name. It refuses builds with pointer compression, the sandbox, or 31-bit Smis (v8dbg_SmiShiftSize), with each reason named. The result is one image row. At a stop, each thread's isolate comes from g_current_isolate_ (G3). In an executable it is a static TLS symbol. In a shared libnode, where it is local and only in the debug package, its module TLS offset is decoded from the exported v8::Isolate::GetCurrent's general-dynamic TLS sequence, and read through the thread's DTV (F28). Threads with no isolate are native threads: libuv's pool, V8's platform workers, the inspector's threads. They are labelled from /proc names, never assumed.

Frames

The native unwinder walks from the thread's registers, by CFI through C++ and by frame pointer through V8 code (G1, G7). For each frame whose code is V8's (a builtin copy, the executable's builtins, or a code page), the model reads the frame's marker slot (v8dbg_off_fp_context):

  • A Smi marker is a typed frame: entry, exit, internal, construct, stub, or Wasm. It is named by its frame type and given CodeRole::Interpreter, so the default view folds it.
  • Otherwise the function slot must hold a JSFunction (instance type in the range the symbols give), whose SharedFunctionInfo names the function and whose Script names the file.
  • Interpreted and Sparkplug frames carry their BytecodeArray and offset in the frame, so their position is the bytecode position table's (F5). For Sparkplug, a native offset first maps to a bytecode offset through the baseline code's own table.
  • Maglev and Turbofan frames give their Code object, which must contain the PC. The function's current code comes through its dispatch handle and the dispatch table, whose location is per line (F18). Its source position table and inlining positions expand the frame into its inlined functions, innermost first. When the function's current code no longer contains the PC, as after an OSR or a deoptimization, the frame gets its function without a line and the reason. It never gets the nearest line.
  • The line comes from Script::line_ends when V8 computed them, or else from the source text. Source in external strings is read from the module file (F6).

A function's name follows V8's rules: the SharedFunctionInfo's name, or its ScopeInfo's function variable, or the inferred name, such as Module._compile. The truth fixtures check names against CallSite.getFunctionName. Scripts whose names start with node: are Node's own and get CodeRole::RuntimeInternal, which folds them like Go's runtime frames. A setting shows them.

Script and function table

A process-lifetime table, like Python's CodeTable, interns scripts and functions by address, with each row's proof: the SharedFunctionInfo's script ID and start position. Because V8's GC can move both, every use re-proves the row, and a moved or reused address misses rather than misnames. Line ends are decoded once per script.

Values, expressions, and views

The object model

  • Primitives. Smis and HeapNumbers are numbers. Oddballs are undefined, null, true, and false. The hole is shown as "uninitialized" (the temporal dead zone). BigInts are shown exactly from their digits; arithmetic takes them up to 128 bits, as Python's ints. Symbols show their description.
  • Strings in every representation: sequential one- and two-byte (decoded as UTF-16, which llnode and OpenTelemetry do not do), cons, sliced, thin, and external, with depth and length bounds.
  • Objects show their properties in V8's order: in-object and out-of-object fields through the map's descriptor array, dictionary-mode properties through the name dictionary, and elements by elements kind (packed, holey, double, dictionary). Accessors are shown as accessors and never called; proxies show their target and handler.
  • Built-ins: arrays, Map and Set (ordered hash tables, in insertion order), Date, RegExp, ArrayBuffer and typed arrays (with the detached state), Promise state and result, errors with their message and stack text, functions with their closure context, async functions and generators with their state.
  • Errors whose stack was never read hold V8's raw call sites. Each names a function, script, and position, so the frame namer formats them as Node would ( at getUser (/srv/routes/users.js:15:22)), marked as formatted by microscope (Q8).

The prototype shows this is achievable exactly (F24). The renderer is a port of the parts of inspect.js the gallery covers, and grows with it. It needs JavaScript's own number-to-string conversion, which differs from Rust's for exponents, and getStringWidth for wide characters. Per-version rules, such as Node 26's computed typed-array length, are named rows in the generated layout, not branches in the reader. A stop's reads go through the stop's page cache, so prototype chains and maps are read once per stop. The global object is found from the selected frame's context, and only a thread with no JavaScript frame uses the isolate's current context (F25).

Every read is charged to the inspection budget, and a malformed object ends with a problem and its address. Views select by a class's constructor name and the script that defines it, and views/javascript-std.views covers Node's library types, such as Buffer, URL, and EventEmitter. Typed arrays and Buffer feed the bitmap, heatmap, and line-plot visualizers through bulk reads.

Variables in a frame

At every stop and in cores, a JavaScript frame shows four things. Its receiver (this) and arguments by position come from the frame. Its context variables come by name from the context chain and each ScopeInfo. Module and script bindings come from the script context table. The global object is shown too. Its stack locals are listed as the interpreter's registers, r0 to rN, with the reason they have no names (F11).

At an inspector pause, the paused thread answers CDP before the all-stop barrier completes (G5). microscope asks for each frame's local scope with Runtime.getProperties (own properties, no accessors invoked, no previews), and binds each name to its register in declaration order, which F17 confirmed on both lines. Sparkplug frames use the same order from the register file's base, which the layout gives. The binding is accepted only if, for every local, the register holds what CDP reported: the same primitive, or an object of the same class. Otherwise the frame keeps unnamed registers and gives the reason. Values themselves are always read from memory, so one presentation path serves every stop. Optimized frames keep their context variables; their stack locals are unavailable, with the reason, because V8 keeps them in the deoptimizer's translation (Q2).

Expressions

Names bind as JavaScript resolves them: register locals where named, then the context chain, then the script context, then the global object. Members follow own data properties and then the prototype chain. A getter, a proxy, an interceptor, or an object without a fast or dictionary map refuses with its reason. x[i] reads elements, and .length and .size read the built-in fields. Comparison and arithmetic follow microscope's exact rules on numbers and BigInts. A C or C++ frame's napi_value or v8::Local<T> is a pointer to a tagged value, which object_types names, so (js)value reaches it as Python's (py) does.

Run control through the inspector

Connecting

  • Launch. microscope sets MICROSCOPE_TRACER to its tracer thread's ID and appends --require <preload> to NODE_OPTIONS, after any value the user set. The preload ships inside microscope and is written once to its runtime directory, readable only by the user. In a process microscope traces, it opens the inspector on 127.0.0.1 port 0 and waits, so breakpoints are armed before the first line of user code (F31). Where the inspector cannot open, it returns and the process runs on.
  • Finding the address. An internal breakpoint on InspectorIoDelegate::GetTargetIds, from the image's symbols, reads the UUID when the server starts. It empties the returned list on every call except during microscope's own connect, so the address is never printed or served (F29). The port comes from /proc (F12). Both breakpoints are internal stops, never published.
  • Release. microscope connects to every node that waits, sets its breakpoints if the process is debugged, and sends Runtime.runIfWaitingForDebugger. It cannot know in advance which processes are debugged, so none of them waits longer than that, at 6–34 ms each (F31).
  • Attach. microscope waits until SigCgt in /proc/PID/status shows Node's SIGUSR1 handler, then sends the signal and waits for the listening socket owned by the process. A process that has not installed the handler, such as one caught at its exec, is never signalled, because the signal would kill it (F31). The same GetTargetIds breakpoint finds and hides the address. A process started with --disable-sigusr1, or with the inspector disabled by policy, gets read-only support, and every JavaScript breakpoint stays pending with that reason.
  • Workers. One connection to the main isolate; NodeWorker.enable with waitForDebuggerOnStart makes each new worker wait until its breakpoints are armed.
  • Transport. A controller-owned task with a bounded channel; TCP_NODELAY, and TCP_QUICKACK re-armed after each read (F10). A disconnect or a target exit resolves every outstanding request with a typed error.

From a CDP pause to an all-stop

JS thread hits a CDP breakpoint or step end
  └ V8 sends Debugger.paused, then parks the thread in runMessageLoopOnPause
controller receives Debugger.paused
  ├ asks the paused isolate for each frame's local scope names       (G5, under 1 ms each)
  ├ stops every thread                                                (the existing barrier)
  ├ judges the hit: condition, hit count, log message, by microscope's evaluator over memory
  └ publishes a Breakpoint, step, or LanguageException stop, or resumes silently
resume
  ├ sends breakpoint changes made while stopped, awaiting their replies (locations stay pending)
  ├ resumes every thread
  └ sends Debugger.resume or the step command to the isolate that owns the execution

The paused thread waits in V8's message loop, not in JavaScript, so stopping the other threads is safe. Nothing is asked of CDP while a stop is published: CDP's answers need the paused thread and the inspector's thread to run, and that would change memory under a published StopId. Edits made while stopped are queued and applied at the next resume, and each location is pending until V8 confirms it, as for Python's agent. An assignment (Debugger.setVariableValue) is an execution that publishes a new stop with StopReason::Assignment, exactly as Python's does.

Breakpoints. A source breakpoint is setBreakpointByUrl on the script's URL, whether path or file://, whose resolved locations are its ready locations. A function breakpoint js:NAME is found through each parsed script's function table (Script::infos), with a breakpoint at each match's start. Conditions and log points are microscope's, never V8's, so their language and semantics are the same as native ones. V8's own conditions would also be unusable: on a hot line they ran the code 20,000 times slower and leaked memory (F20). A microscope condition costs a pause and resume per hit, about 1 ms with the all-stop, which the documentation states for hot lines. Native breakpoints, watchpoints, signals, and catchpoints work as before and now show JavaScript frames.

Steps are V8's stepInto, stepOver, and stepOut, owned by the isolate that paused. A pause in another isolate does not complete the step, and is a stop of its own. V8 steps across await itself. From an inspector pause a step is V8's. From a native or interrupted stop whose selected thread has an isolate, a JavaScript step means “to the next user JavaScript statement”. microscope sends Debugger.pause, resumes, and then repeats stepInto while the top frame is a node: or skipped script, within a step budget, because blackboxing does not move a pause that lands in Node's code (F19). Python's steps from a native stop are refused instead, since its agent cannot pause from outside. Stepping into a Node-API addon's C function uses the callee's callback address, read from its function template, with a native trap in the step's plan. A native step that returns into V8 code becomes a CDP Debugger.pause on that isolate, which stops at its next JavaScript statement.

Interrupts. An interrupt sends Debugger.pause to each isolate and waits up to 50 ms. Running JavaScript pauses in about 1 ms, so the interrupt becomes an inspector stop with named locals. A thread that is idle, in a system call, or in a long C++ call cannot pause (F19), so the controller makes the native all-stop as today. A pause request cannot be withdrawn, so the controller records it as outstanding per isolate. When it fires after the next resume, the controller resumes it silently, with no stop and no event to the client. The scripted inspector tests every ordering of that late pause against breakpoints and steps.

Exceptions. The two filters map to setPauseOnExceptions (caught and uncaught). The exception value comes from the pause and is read from memory as any value is.

Detach removes every breakpoint, resumes the isolates, and closes the connection. An inspector that microscope started, by signal or by its preload, is closed last with setImmediate(() => process.getBuiltinModule('inspector').close()), which stopped the listener on 22, 24, and 26 while the program ran on (F31). An inspector the program started itself stays open.

Async and tasks

Await chains. A running async function's own promise lists its reactions. A reaction whose handler is an await continuation names the awaiting JSAsyncFunctionObject, whose function, context, and suspended bytecode offset make a logical frame. Repeating this gives the chain of callers suspended in await, appended below the running frames, as tokio's awaited-by frames are. Every step follows a type, and the chain ends with its reason at the first reaction that is not an await continuation, such as Promise.all or a user's then.

Tasks. The event loop's pending work is in Node's own lists: each environment's handle and request queues, which nodedbg_ describes. Each handle (socket, server, child process, message port) and request (fs, DNS, write) is a task, with its kind, state, and the JavaScript callback's function and place where its wrapper holds one. The prototype read all of these on both lines (F23). Pending promises that nothing references from a list are not enumerable without walking the heap, and are not shown (Q4).

  • Classes come from each wrapper's vtable, matched to the executable's vtable for symbols, so a node::TCPWrap is named exactly. The libuv handle behind it must point back at the wrapper, or the entry is a problem.
  • Callbacks. Where the callback is one of Node's wrappers, the task shows the user's function it captured, when one capture holds a function from a non-node: script. Otherwise it shows the wrapper.
  • JavaScript timers share one libuv timer. The task list shows that timer's next expiry until the timer lists in internal/timers are reached. They are reachable through the module context of Node's timer callback, which the Environment holds without a nodedbg_ offset. N4 reaches it through a decoded accessor (F25), because nothing is proposed upstream (Q6).
  • Thread-pool jobs such as Node 26's fs.readFile, zlib, and crypto are in neither list. They appear through the libuv pool thread running them, with that thread's native stack, and are named “thread-pool job” without a callback.
  • Node 24's nodedbg_ offsets are zero in the file, so tasks are read only from a live process or a core, which holds the initialized .bss.

Profiling

V8's frames are on the native stack, so a perf sample's stack copy already holds every JavaScript frame's frame pointer, function slot, and bytecode offset. What a later read cannot trust is the heap behind the function slot, because the GC can move it. The BPF V8 walker, attached to the sampler's own events as Python's is, follows the frame-pointer chain. For each JavaScript frame it records the SharedFunctionInfo address and its proof (script ID and start position, two more reads), plus the bytecode or code offset. The symbolizer names a frame only where its proof matches the table's row, and counts the others as unknown. The stopped and live snapshot engines use the debugger's reader directly. The builtin alias modules (G1) and code-page pseudo-modules make native stacks continue through JavaScript, which today's sampler truncates at the first V8 frame.

Programs started with --perf-basic-prof or --perf-prof already write a perf map, which microscope reads today. Their names serve where the walker cannot read a frame.

Instrumentation. sdk/node is a Node-API addon over the probes library's run-time sites (ABI 2), with zone, plot, message, and label, as the Python package has. Programs opt in by importing it, and microscope writes to no program that did not.

Several processes. Under process following (G8), each member binds its own V8 layout, isolates, and walker state, and binds again after each exec. A recording of a group keeps each sample with its process, so npm start profiles the app, not npm. System call tracing does the same.

System calls

The ptrace engine reads the stopped thread's stack through Stacks with the same reader, so each call names the JavaScript line that made it. Most calls come from libuv's thread pool, whose stacks hold no JavaScript; they show the request and its callback's place, from the task lists, where provable. The BPF engine runs the V8 walker in sys_enter, and the dual-engine tests hold the two engines to the same frames. Catchpoints stop with mixed stacks unchanged.

Fast feedback

Node starts in about 40 ms, and a CDP round trip is under 0.1 ms, so each scenario should cost tenths of a second. Tests wait for READY lines and CDP events, never for time. It is tested on hand-worked maps, by property tests against a linear-scan oracle, by a fuzz target, and differentially against Node's own SourceMap on 22, 24 and 26 over 15,790 queries. Node differs in two ways, and the spec sides with microscope both times. Node's findEntry answers a position before its line's first segment with an earlier line's segment, and it reads past the end of mappings when the last segment has 1 or 4 fields. Not yet used by frames or breakpoints.
  • Compiled frames (d5988842). The model finds a frame's code among its function's candidates: its current code (through the dispatch table from 13.6, the function itself before), its baseline code, and its OSR code, which V8 caches only as weak references in the FeedbackVector. It uses the candidate whose instructions hold the frame's pc and never a nearby one. Sparkplug frames map the pc to their bytecode through the bytecode offset table and kBytecodeSizes.
  • Maglev and Turbofan frames, inlined functions included, read as V8's OptimizedJSFrame::Summarize reads them (d1fbe353). The safepoint table maps the call to a deoptimization index, and the index's translation names each frame with its function and bytecode offset. The code's own position table is not enough: nixpkgs-24's Maglev code keeps an empty one, because positions are collected only when a profiler asks. The safepoint and translation formats and the opcode table are generated per version from V8's headers and stale-checked. Builtin continuations, construct stubs, and Maglev's function-entry summary follow V8, and inlined WebAssembly and compressed translations are refused by name. On all six matrix builds, every tier's frames match CallSite, live and in cores. Planted bugs (reversed inlining, a wrong bytecode offset) fail the tier test on all six.
  • Function names by JSFunction::GetDebugName (ff5b18ef). A function whose map no longer keeps the original name accessor is named by its name data property, found as GetDataProperty finds it. The lookup reads fast maps' descriptors (in-object and property-array fields), NameDictionarys, and the prototype chain, and refuses a Swiss dictionary by name. This names symbol-keyed methods such as [nodejs.internal.kHybridDispatch]. The stacks.js worker redefines names as data, in dictionary mode and on a prototype, and planted bugs in each path fail the frame tests. No fixture reaches the property-array path yet; N2's values will.
  • Budget check: in a release build, describing a backtrace of 113 frames (100 interpreted JavaScript frames of one recursive function) took 0.58 ms on average over 8 backtraces on Node 26, measured by the code_frames timing span. That is within the 1 ms budget without the script and function table, which remains to cut the roughly 93 allocations per frame.

Gaps:

  • None on the six matrix builds: the frame tests' list of known gaps is empty.
  • Debian's builtins need the embedded blob's bounds, read from the process at each stop, since the stripped libnode has no static anchor for them (in progress). Debian also exports neither kBytecodeSizes nor the dispatch table, so some of its compiled frames will name why they have no place.

Decision needed: isolates in the thread list. The walkthrough shows isolate 1 beside each thread, but the public model section allows only three changes, and a thread snapshot has no runtime labels today. RuntimeModel::thread_labels reaches only the profiler. The options are a public field on thread snapshots for runtime labels (Python's GIL holder could use it too), or keeping isolates to the profiler and the threads' /proc names. Also open: an isolate's number needs a process-lifetime table to stay stable across stops. Its address would be stable but unreadable. Not started until decided.

What this leaves for the next runtime

After Python and Node, the shape is settled enough to state. A runtime is a provider (static layout from the target's own self-description, completed by generated data and checked where both speak), a runtime model (one stop, through RuntimeStop, with typed partial results), and, if it needs control, a transport filling the shared installation record (G4). Its frames take one of two forms. They are heap frames placed by counting activations, as CPython's, or native frames in runtime-owned code that the model names (G2), as V8's and HotSpot's will be.

For HotSpot, gHotSpotVMStructs is the self-description, as v8dbg_ is here. Its frames sit on the native stack in the code cache, so G1, G2, and G7 serve it unchanged. JVMTI or JDWP is its transport, which would fill the same record CDP does, and its JDK LTS lines would follow the same version policy. Ruby's YJIT frames and its rb_control_frame_t chain are a CPython-shaped heap chain with a JIT beside it. Nothing in this plan's public model is V8's; each addition names a fact a JVM or Ruby frame also has.

Questions and decisions

Each question below was decided on 22 October 2026. Each card marks its decision in bold, with the reasoning beside it.

Q1

How does microscope learn the inspector's URL?

Decided, as recommended: launch with --inspect-publish-uid=stderr, which keeps the UUID secret from other local users (/json/list answers 404), and read the URL from the banner Node prints.

Revised after experiments, with the same goal of keeping the address private. The banner cannot serve a child, whose stderr microscope does not own: node --test swallowed it. Any --inspect flag also changes how node --test runs (F30). microscope now reads the UUID from the process with a breakpoint on GetTargetIds and hides it, so it is neither printed nor listed, on launch and on attach alike (F29). The inspector itself is opened by the launch preload (F31). stderr keeps Node's fixed For help and Debugger attached. lines, which carry no address.

Q2

Names of stack locals outside inspector pauses

V8 names them only by reparsing source (F11). An exact reader could do the same: parse the function with a JavaScript parser crate and allocate as V8 does. Its result is checkable against ScopeInfo's context locals and the register count. Decided, as recommended: not now. Unnamed registers are honest, and the CDP binding covers the common case. Revisit with a prototype measured against the CDP differential.

Q3

Node 22?

Decided: yes, until its end of life on 30 April 2027, against the recommendation, which was to skip a line with six months left. F27 showed the cost is smaller than assumed. It is the 13.6 table encoding, not a third. Its direct code field is simpler than leaptiering, and its Torque output matches the binary. It costs two flake entries (22, nixpkgs-22) and one generated layout, all deleted in April 2027.

Q4

What is a Node task?

Decided, as recommended: pending event loop handles and requests, from Node's own lists, named "handles" in clients. Every pending promise would need a heap walk, which the runtime-model rules forbid. Await chains attach to the frames that run them instead.

Q5

Shared libnode builds?

Decided: supported from the start, against the recommendation to wait. The flake pins Debian's build by hash, never the host's. F28 showed it is practical. Debian testing ships Node 24 as libnode137, with every v8dbg_ symbol in the dynamic table and values equal to the official build's. Each thread's isolate is found by decoding the exported v8::Isolate::GetCurrent, so no 1.6 GB debug package is needed. The pinned closure runs under a rootless namespace.

The user experience: someone who ran apt install nodejs on a supported line gets the same stacks, values, cores, breakpoints, and steps as with an official build. Detection, isolates, and the namespace test group are N1 work (debian-24).

Q6

Contribute upstream?

Decided: no, against the recommendation to propose missing metadata to V8 and Node. Users of today's lines see no difference, since an accepted patch would ship in Node 27 at the earliest. The cost is maintenance. Every new line keeps the whole yearly derivation: generated layouts, plus the facts decoded from machine code (F25). A line whose accessor changes shape is refused by name until microscope is updated (Risks). Individual JavaScript timers are reached through a decoded accessor rather than a new nodedbg_ field.

Q7

Programs started through npm, npx, --test, or --watch?

Many users never type node. They run npm run dev, npx, node --test, or node --watch, and in every one the user's code runs in a child microscope does not follow (F26).

Decided, as recommended: do G8 as its own plan, alongside N1–N2, so it lands before N3's exit. The order follows the common chains:

  1. Report every child that is let go (G0).
  2. Follow exec into a new image, which covers env node, bash -c, and version-manager shims, and launch #! scripts, which together cover ./cli.js, npm, and npx (G1).
  3. Host every process on one tracer thread (G2), then follow children, decided once their program has loaded, which covers npm's grandchild, --test, and --watch (G3).
  4. Present the group in every client, including one DAP adapter (G4), and retire the held-child hand-over (G5).

Until then, the refusals name the direct form, the docs give each tool's recipe, and a batch run fails on an exec it did not follow. Python gains the same.

Q8

Format error stacks V8 has not formatted?

An error whose .stack was never read holds raw call sites, not text (F24). The choices are: show only the message and name, marked “stack not formatted”; or format the call sites as V8 and Node would, with function names, receivers, positions, and async frames. Decided, as recommended: format them, in N2. Each call site's function, script, and position go through the frame namer that stacks already use, and the gallery compares the result with the stack text the fixture reads afterwards. Source-mapped positions follow G6. Where a call site cannot be read, that frame says so and the rest are shown.
