Python, the first managed language

Every language microscope supports today compiles to machine code described by DWARF. Python does not: its frames live on the heap, its functions are objects created at run time, its values are typed by a pointer in each object, and its source lines come from tables inside those objects. This plan says how microscope can read all of that from outside the process, exactly and cheaply. It covers the debugger, values, views, visualizers, sampling and instrumented profiling, and system call analysis. It fits Python into the architecture microscope already has, a debug-information provider plus a runtime model as Go has, so that Node, Bun, and the JVM can follow the same path without reshaping the public model again.

Summary

Read, don't run. The target stays read-only unless a debugger feature cannot work any other way. CPython 3.13 and later carry a table of their own struct offsets, _Py_DebugOffsets, in an ELF section named .PyRuntime. For 3.12, which has no table, microscope builds the same table from offsets generated from 3.12's headers. With that table and a small set of per-version constants that microscope generates and tests, microscope can read threads, Python stacks, code objects, line numbers, locals, and common values straight from process memory. This needs no code in the target, no stop beyond the ones microscope already makes, and works the same on core dumps. A prototype in this branch's research did exactly this against 3.13, 3.14, 3.15.0b3, and free-threaded 3.14 (see Findings).

Run only what must run. Only the debugger may put code in the target, and only for Python breakpoints, stepping, exception stops, and writes the user asks for. These need something inside the interpreter to notice a line or a raise. That is a small agent, installed with PEP 768's attach protocol (3.14+) and built on sys.monitoring, which costs nothing at a location until a breakpoint is there. It does not talk over a socket or evaluate anything. When an event fires, it traps into microscope through a native hook, the same machinery that reports Go panics today. microscope then stops every thread, as it always does, and does all reading and evaluation itself.

Merge stacks only where it can be proven. One native _PyEval_EvalFrameDefault activation runs many Python frames, and Python frames are not on the native stack at all. microscope splits the Python frame chain at the interpreter's entry frames and splices each segment in place of the activation that runs it. A profiler sample can show a mixed stack only if the Python frames were read at the same instant as the registers. That takes a BPF program on the sampling event (privileged) or a stopped snapshot (unprivileged, pauses the target). A non-blocking reader is cheaper but gives Python-only stacks, and it counts the samples it cannot prove complete instead of guessing.

Python is one more runtime, not a new layer. Go support is a debug-information provider that turns module bytes into image tables, plus a runtime model that reads a stop. Python is the same two pieces. The provider turns .PyRuntime into a one-row image table of validated offsets and assigns the interpreter's code roles. The runtime model reads threads, frames, objects, and asyncio tasks through RuntimeStop, which the debugger, the profiler's snapshots, and the syscall tracer already share. A review of the codebase against this plan (Codebase review) found existing homes for nearly every concern. It found fourteen places where existing code is narrower than it needs to be. Each is generalized in its own commit, with a test that involves no Python (Groundwork). There is no src/managed layer and no new trait family. V8 and HotSpot would be a provider and a runtime model too.

The four decisions that most change the work are recorded in Decisions. The smaller ones in Open questions each have a recommended default. Nothing below depends on a choice that has not been made explicit in one of those two places.

Findings

The research read the CPython headers of every version in question, the PEPs, and the source of py-spy, pystack, the OpenTelemetry eBPF profiler, and pydevd. It also ran experiments against interpreters from the pinned nixpkgs and from Fedora: a 230-line out-of-process frame walker, injection timing, native stack shape, and JIT and trampoline probes. The prototypes are throwaway Python and are not checked in. Each finding below changed the plan.

F1

The offsets table is versioned, not self-describing

_Py_DebugOffsets sits at offset 0 of the .PyRuntime section: an 8-byte cookie xdebugpy, PY_VERSION_HEX, a free-threaded flag, then nested tables of u64 offsets. Each minor version inserts fields in the middle (table below), and there is no total size, so a reader must know each minor version's schema. CPython's own reader requires an exact major.minor match, and for prereleases an exact version match.

F2

Reading from outside works on every version tried

Using only /proc/PID/mem and no stop, the prototype printed every thread's Python stack with correct lines, plus locals including a 101-bit int, a dict of mixed values, and a list of instances. It ran against 3.13.15, 3.14.7 (nixpkgs and Fedora), 3.15.0b3, and 3.14.4t. One all-threads stack read took 42–56 µs in Python, with 97–121 small reads (2.1–2.9 KB). A Rust reader that reads a whole frame per call and caches code objects needs about one read per frame.

F3

What the table leaves out is where bugs live

Three bugs appeared in one afternoon, all outside the table. A dict-keys header at the wrong offset showed populated dicts as {}, which looked correct. The str state bitfield has a different layout in free-threaded builds. And free-threaded threads run their own copy of the bytecode (tlbc_index), so the instruction offset from co_code_adaptive fell outside the code and the prototype printed line None. With unlucky addresses it would have printed a wrong line. Every layout outside the table needs a generated constant, a range check, and a fixture.

F4

One native activation runs many Python frames

Since 3.11, Python-to-Python calls do not recurse in C. In the fixture, eight Python frames (<module>, six recurse, leaf) all ran inside a single _PyEval_EvalFrameDefault. The sleeper thread has two activations separated by context_run and method_vectorcall. Python frames live in heap data-stack chunks, not on the native stack. Entry frames mark where each activation's segment begins. Their owner value is CSTACK = 3 in 3.13, INTERPRETER = 3 in 3.14 (where CSTACK is 4), and 3.15 drops CSTACK.

F5

A perf sample cannot see Python frames

microscope's sampler copies registers and up to 16 KiB of stack. The Python frames, code pointers, and instruction pointers are on the heap, so the copy never contains them. Reading them later is reading a different instant. A mixed stack therefore needs the Python frames read in the same instant: in BPF at the sampling event, or with the thread stopped. CPython's own 3.15 sampler, Tachyon, reads without stopping by default. It accepts torn stacks and detects incomplete ones with the new base_frame sentinel.

F6

Frame pointers arrive; the JIT stays off

PEP 831 is Final: 3.15 builds with -fno-omit-frame-pointer -mno-omit-leaf-frame-pointer by default. Fedora already does. Every _PyEval_EvalFrameDefault examined (Fedora 3.14, nixpkgs 3.13 and 3.14) keeps rbp. Fedora's 3.14 builds the experimental JIT but leaves it off. In our test PYTHON_JIT=1 did not activate it, and no anonymous executable mapping appeared. 3.15's JIT registers DWARF unwind data through the GDB JIT interface. A June 2026 report says the Steering Council paused new JIT work. That report is unverified; either way the JIT is a later phase.

F7

Trampolines already break microscope's native stacks

python -X perf maps an anonymous executable page and writes /tmp/perf-PID.map with lines like py::leaf:/…/target.py, one per code object entered from C. microscope's sampler ends a stack at any address outside a file-backed module (Truncation::UnmappedAddress), so a user who enables this today gets shorter stacks. Perf maps and frame-pointer unwinding through mapped JIT ranges are a general fix that Node and the JVM need too.

F8

PEP 768 can target any thread, not only main

sys.remote_exec asks the main thread to run a script at its next eval-breaker check. It ran 0.24 ms after the call against a spinning main thread, 500 ms later when main woke from a 0.5 s sleep, and never while main was blocked in time.sleep. The request fields, though, are per PyThreadState. Writing them into a worker thread's state while the process was stopped made the script run on worker 0.12 ms after resume (3.14 and 3.15), even with main blocked. microscope can choose a thread that is executing bytecode.

F9

sys.monitoring makes idle breakpoints free

PEP 669 (3.12+) instruments bytecode per code object and per event. A location that returns DISABLE stops costing anything, and a code object with no local events runs unchanged. pdb uses it from 3.14, and pydevd uses it for line breakpoints, stepping, and exceptions. Tool IDs are shared: if a target already runs debugpy, the debugger ID is taken, and the agent must say so.

F10

3.12 has no table at all

3.12 has a .PyRuntime section but no cookie or offsets. The prototype read the first word as 01 00 00 00 …. py-spy, pystack, and austin each keep hand-copied or bindgen-generated structs per release. 3.12 also differs in shape:

  • frames hold f_code and prev_instr;
  • the current frame is reached through cframe;
  • stack entries are untagged.

Neither 3.12 nor 3.13 has sys.remote_exec, so breakpoints there need a separate bootstrap.

F11

The model is bound to images

Several parts of the model assume a sealed ModuleImage:

  • SourceLocation.file is a SourceFileId within an image, and clients resolve it through that image.
  • TypeReference names a type node in an image's graph.
  • FunctionInfo uses an image's FunctionId.
  • Every resolved breakpoint is an int3.
  • The capture's FrameKind rejects unknown kinds.
  • A syscall CallStack holds only addresses.
  • Probe sites are static ELF records.

The model does have one place to start: FrameKind::Async and Awaited frames have no machine context.

F12

The pinned 3.15 is a beta, and betas differ

nixos-26.05 provides 3.12.13, 3.13.13, 3.14.4, and 3.15.0b3, plus free-threaded 3.13, 3.14, and 3.15b3. 3.15.0 was released on 9 October 2026. Its thread-state table adds last_profiled_frame_seq, which 3.15.0b3 lacks. The matrix must use 3.15.0 final, which it takes from python-build-standalone (matrix), and a prerelease is supported only by its exact version.

Architecture: a provider and a runtime model

Go support has two halves. src/debug_info/gopclntab.rs turns module bytes into image tables and code roles. src/runtime_model/go/ reads goroutines at a stop through RuntimeStop. Python gets the same two halves and nothing beside them:

  • A debug-information provider, src/debug_info/cpython.rs. It reads .PyRuntime and Py_Version from the module's own bytes, validates them, and writes one row of offsets into a new image table, src/image/python.rs. It also gives the eval loop and the call machinery their code role. Everything it produces depends only on module bytes, so it is cached and validated with the rest of the image.
  • A runtime model, src/runtime_model/python/. It is detected by runtime_model::detect like Go and tokio. It implements RuntimeModel, and it reads only through RuntimeStop. That trait already serves the debugger (ProcessStop), the profiler's live snapshots (LiveStop), and tests over synthesized memory. So the debugger, the profiler, and the syscall tracer share one reader, and none of them owns a second copy.

The managed-runtime idea survives as a list of concerns that a runtime fills in. It does not survive as a layer. Each concern already has a home:

The rules that already govern the codebase apply unchanged:

  • Static facts, such as which image is a Python runtime and where its eval loop and sections are, go into image tables through the loader, and become code roles.
  • Dynamic facts are read at one stop and never carried into the next. The code table is the one cache that spans stops, and it re-proves each row before using it.
  • Only the controller thread calls ptrace. The runtime model cannot write; it returns the writes it needs as data, and the controller makes them (G7).
  • Records are flat, dense, and Copy. A layout is a fixed struct of validated offsets, not a hash map of names.

Codebase review

This plan was checked against every page under dev/ and the code it would touch: the runtime models and stack splicing, the evaluator and views, the public model and protocol, breakpoints and run control, the profiler and capture format, the syscall BPF engine, image loading, and the test and simulator infrastructure. Each card is something the review found that changed the plan. File references are to main at 5efc6d13.

R1

Go is the template, so there is no new layer

An earlier draft put Python in a new src/managed layer with one trait per concern. Every concern turned out to have a home already (table above). A parallel layer would have duplicated discovery, stop-scoped reads, hooks, and splicing, and V8 would have inherited the duplication. Python is a provider plus a runtime model, as Go is.

R2

The layout is a static fact

_Py_DebugOffsets is a static initializer in the file's .PyRuntime section, and Py_Version is a constant. Both depend only on module bytes, so the validated layout belongs in an image table: built once, cached, revalidated on a cache hit, and never re-read per process. The provider reads the section from the module itself, not from a separate debug file, where data sections are NOBITS. embedded_views (dwarf.rs:1558) reads the debug object, and the provider must not copy that.

R3

Go's "never a table of versions" rule needs a stated exception

runtime_model/go/layout.rs:1-6 says offsets come "from DWARF by name, never from a table of versions". Python's equivalent is the target's own table, read by name under a schema per minor version. Generated per-version constants are allowed only where the target describes nothing: all of 3.12, and the few fields 3.13+ leave out (F3). The exception is stated in the provider's module comment. When an interpreter in the matrix has DWARF, a test checks every constant against it. Q5 shrinks the exception upstream.

R4

Fewer public types than drafted

  • Sources and names. RecordedPlace already names a source by path, and TaskLocation already pairs it with a function name. So frames take an optional recorded frame instead of a SourceRef enum threaded through every SourceLocation.
  • Breakpoints and exceptions. BreakpointSpec::Source is keyed by path, so Python breakpoints need no new spec. ExceptionFilter and RuntimeHook carry Python exceptions with two new constants. StopReason::Breakpoint serves Python hits, because no client reads its address.
  • Not needed yet. A managed function identity in FunctionInfo and a capability report can wait until typed errors prove too little.
R5

The splice exists, and it inserts

splice_driven (async_frames.rs:299-425) inserts a future chain before the poll frame that drives it, and keeps the poll frame. Python does the same: each segment goes before its eval-loop activation, which stays in the stack, hidden by its role. Replacing the activation would break resolve_presented_frame, which sizes its unwind on the assumption that every activation yields at least one frame (frames.rs:465). The driver test keys on the code role, because a symbol-only libpython has no FunctionInfo.

R6

Pending breakpoints exist

When a library loads, the loader breakpoint triggers refresh_libraries, and reresolve_breakpoints (libraries.rs:91-153) re-runs resolution and diffs owners. A Python import is the same event from a different source. The agent's import notice runs a second resolver beside resolve_in_modules. Conditions, hit counts, and log messages (judge_condition) are reused as they are.

R7

microscope's integers stop at 128 bits

Exact is a sign and a u128 magnitude (number.rs:61-68). The earlier claim that Python ints fit exact arithmetic at any size was wrong. Display is still exact at any size: the presenter prints an int from its digits. Arithmetic on an int beyond 128 bits fails with a typed error that says so. Widening Exact into a bignum would touch Key, Constant, and every Copy use, so that change waits for a need.

R8

Dynamic types exist only in presentation

cpp_dynamic, rust_dynamic, and go_dynamic (presentation.rs:1641-1806) choose a DWARF type when a value is shown. Binding is fully static. So self.items[3].name needs one new type category in the evaluator, whose member, index, and comparison steps resolve at run time (G11). The other finding is that Rust-coded presentations already exist. built_in() presents Go pointers, sum types, Rust tuples, and coroutines, although plans/views.md says no native views exist. The Python presenter joins them, with its stated reason.

R9

Two of the three sampling engines exist

The profiler already takes stopped and live runtime snapshots for Go and tokio (profiler/tasks.rs). It records each pause, and reads live through LiveStop, which implements RuntimeStop. The Python "snapshot" and "live" engines are those snapshots taken on threads. They are not new engines. Two existing gaps matter:

  • Live snapshots run detection only on /proc/PID/exe (session.rs:481), so they would never see a shared libpython.
  • An unlearned live snapshot silently falls back to a stopped one (session.rs:553-557), against the rule that engines never switch by themselves.
R10

The BPF engine joins the perf sample instead of replacing it

The draft had a BPF program emit the whole sample. That would duplicate the sampler, cap the stack copy at 8 KiB instead of perf's 16 KiB, and put samples on a ring apart from the mapping records that normalize addresses. Instead, a perf_event program attaches to the sampler's existing events with PERF_EVENT_IOC_SET_BPF and returns 1, so perf still writes its normal sample. It writes the Python frames into the same CPU's ring, just ahead of the sample, so the existing sort orders them with no clock join. aya cannot attach to an existing descriptor, so this needs a raw ioctl beside set_output.

R11

CPython can never run in the simulator

The simulator's CPU implements only what the golden corpus executes. The draft's claim that the agent was "modeled" was wrong. The split is:

  • Reading is tested purely, over synthesized memory, through RuntimeStop.
  • The agent's trap protocol is simulated with a golden C program that plays the agent: it fills a mailbox and calls the hook.
  • The BPF record is modeled in sim/tracing.rs or stated there as unmodeled.
R12

Run-time probe sites need their own key space

A site's key is today the i32 offset of its state byte from the control block (probes.rs:128-130). A heap byte more than 2 GiB away overflows that. A definition record in a ring could also be read after another thread's ring uses it. So run-time sites live in an append-only registry, which the control block points to from its reserved bytes at offset 56, with keys of their own. The decoder accepts ABI 1 and 2, so existing binaries keep working.

Data layout

Python support is designed from its data and how that data is read, as dev/style.md asks. There are four lifetimes, and each has one owner:

  1. the image;
  2. the process;
  3. the stop;
  4. the capture file.

No table holds a pointer, Rc, or Box into another. Rows refer to each other by dense u32 IDs, and variable-sized data lives in pools reached by spans.

  • Newtypes for every space. Process addresses are VirtualAddress, image facts are ImageAddress and ImageRange, and struct offsets are FieldOffset. CPython's own numbers are normalized at the provider boundary into PyVersion and FrameOwner, so no per-version number reaches the model. APIs use Option<Id>. NONE appears only inside zerocopy image records, as everywhere else.
  • Small hot records. A PythonFrame is 24 bytes. Names, line tables, and local-name lists are variable-sized, so they sit in pools. A line is decoded from the pool only when a frame needs it.
  • Batched reads. A frame is one read of frame_size bytes. A code object is decoded once per process, and its proof is one small read at each later use. The whole PythonStop is built in one pass, not frame by frame on request.
  • Invariants. CodeTable and PythonStop each get a check_invariants run under debug assertions: spans in range, frames contiguous per thread, threads sorted, every CodeId valid. Each has a test that corrupts the state and expects the panic. Nothing asserts on tracee bytes; a bad read is a typed error.
  • No unsafe code in microscope. Every read goes through existing safe paths. The hook library's one exported function is empty, and it lives in sdk/, under that crate's own Miri tests.

Debugger

Finding interpreters

A module is a Python runtime when its image has a .PyRuntime section. That covers libpython3.x.so (Fedora, nixpkgs), executables that link it statically (Debian, Ubuntu, python-build-standalone as installed by uv), and programs that embed Python (Blender, uWSGI, PostgreSQL's PL/Python). The section's bytes give the cookie and version without running anything: the table is a static initializer, so it is present from load. Interpreters exist only after Py_Initialize. Until then the runtime reports itself as initializing.

For 3.12 there is no table in the target. microscope supplies one, generated from 3.12's headers for each patch release in the matrix and selected by Py_Version. A 3.12 patch release that is not in that list is unsupported until its offsets are checked. The provider reads the table once, when the image loads. It validates the cookie, version, free-threaded flag, and every offset against the section size and the reported struct sizes, and seals the result into the image (Data layout). The runtime model copies that row when it binds. A version microscope does not know is Unsupported, with the version it found. It never falls back to the closest known version. Threads map to tracees by native_thread_id. Native threads with no thread state show native frames only. All interpreters are walked, and subinterpreters are labeled by ID.

Stacks

At a stop, after the native unwind, the stack integration hook walks the thread's frame chain from current_frame:

  • It reads one frame per memory read.
  • It keeps the frames owned by the thread or a generator.
  • It cuts the chain into segments at entry frames.
  • It pairs segments with the thread's eval-loop activations, innermost first. splice_driven then inserts each segment before its activation, as it inserts a future chain before its poll frame today. The activation stays, hidden by CodeRole::Interpreter (R5, G4).

The walk builds the stop's whole PythonStop in one batch. Every backtrace at that stop slices it, so no frame is read twice.

On 3.15, reaching base_frame proves the walk complete. On earlier versions, the walk is complete when it ends at a null previous with every owner and type valid.

If the counts disagree, or a segment cannot be placed, microscope keeps the native stack. It appends the Python segments it could not place as a separate, labeled group and states the reason. It never interleaves by position. An instruction pointer outside its code object's bytecode, including the free-threaded thread-local copy, gives a frame with an unavailable line, never the nearest one.

Run control

Native breakpoints, signals, catchpoints, watchpoints, and pause all work as before. Their stops now show Python frames and locals. Python breakpoints, stepping, and exceptions come from the agent (next section). Those stops are ordinary all-stop stops with the existing reasons: Breakpoint with no address, a step's completion, or LanguageException. The same StopId and ExecutionId rules apply. Breakpoint ownership follows the native split. The agent's arming is a physical installation, and the user's breakpoint records keep their options. Python breakpoints resolve at import through the same reresolve_breakpoints pass that library loads use (R6, G9). Stepping is owned by one thread, or with asyncio by one task. A step that another thread completes is not a completed step, as with goroutines today.

Assigning to a Python local from outside would break reference counts. Writes therefore go through the agent, using 3.13's write-through frame.f_locals (PEP 667), and are a later phase. Until then, Python values are read-only, with an explicit reason. A hardware watchpoint on a fast-local slot can implement watch x for a Python local, scoped to the frame's life. That is also a later phase.

asyncio

The .AsyncioDebug section (3.14+) lists tasks per thread and per interpreter, each task's coroutine, and who awaits it. microscope reads it into neutral tasks: running, runnable, or blocked; a name; and a logical stack built from the coroutine's embedded frame and its awaited by links. Walks are bounded, and a cycle ends with a problem. This is the tokio design with a different source of facts. gevent and greenlet switch C stacks and are out of scope.

Core dumps, fork, exec

Everything that only reads, which is stacks, values, expressions, views, and asyncio tasks, works on a core dump through the post-mortem path. Agent features report themselves unavailable there.

  • Fork. A forked child inherits the agent. The agent registers an after_in_child fork hook that disarms it, and microscope re-arms it if a client adopts the child.
  • Exec. A program that execs into Python (shell wrappers, pyenv shims, console scripts) is found when libpython or a .PyRuntime image is mapped. uv run does not exec: it spawns Python as a child and waits (checked with uv on Fedora 44), so it needs follow-forks, or the user launches .venv/bin/python directly.

Clients

The CLI, DAP, and web page render interpreted frames with their recorded path and no address, through the one src/present helper (G5). DAP reports them without instruction references and with Locals, Globals, and (for closures) Cells scopes instead of Registers. The web stack shows a small language mark per frame and the hidden-machinery fold. Python syntax highlighting joins the CLI and web tokenizers. The VS Code extension registers Python breakpoints. Nothing about Python's object model reaches the clients: they see presented values as for any language.

The agent

The agent is the only Python code microscope puts in a target. Its job is narrow: turn interpreter events into native traps. It holds no breakpoint conditions, evaluates no expressions, opens no sockets, and starts no threads. Its transport uses sys, ctypes, json, _thread, and _weakref. It runs inside the target's interpreter, not inside microscope, so the policy that microscope embeds no interpreter is unchanged.

Installing it

microscope installs the agent through PEP 768's protocol in launch, attach, and exec alike, because it is the one path that is safe at an arbitrary stop:

  1. Write the agent to a file only the target's user can read, inside the target's mount namespace. Use /proc/PID/root, as module loading already does.
  2. While all threads are stopped, pick a thread that is executing bytecode, preferring the selected one. Write the script path into its thread state, set the pending flag, and set the eval breaker's stop bit. All-stop makes this read-modify-write safe, which sys.remote_exec itself is not. The runtime model only computes these writes. It returns them as data, and the controller performs them through writes.rs under the current StopId, where they are recorded and simulated like any other write (G7).
  3. Resume. The agent runs at that thread's next safe point (0.12 ms in the experiment), registers its tool, and traps once to say it is ready. microscope deletes the file.

On launch, microscope stops at evaluation-loop entries and waits for _PyRuntime.initialized before requesting the agent, so the program's first line can be armed. The first entry itself occurs during bootstrap, before _io is available. Tail-call builds may require the _TAIL_CALL_start_frame entry instead of _PyEval_EvalFrameDefault; see P4.7.

If no thread runs bytecode, for example when all of them are blocked in C, the agent waits, and Python breakpoints stay pending with the reason "no thread is running Python." It is never forced in by a signal. If the target disabled remote debugging (PYTHON_DISABLE_REMOTE_DEBUG or -X disable-remote-debug), pending breakpoints give that as their reason, and stacks, values, and profiling still work. 3.12 and 3.13 have no injection protocol. They get every read-only feature, and how they get breakpoints is Q1.

Trapping into microscope

When a monitored event fires, the agent calls its companion’s C-ABI hook. Its arguments carry the event kind, breakpoint or step ID, and report argument in the calling thread’s registers. This implemented transport replaces the initial mailbox proposal, avoiding shared event state between free-threaded callbacks. microscope keeps a runtime-owned int3 on the hook, as it does on gopanic. Unlike an exception hook, it is always armed while the agent runs, and each hit decides whether to stop or continue, as Go's stack-move sites already do privately. That is G6. The hook lives in a companion image, the hook library, which the Python model resolves through G8. microscope stops all threads, reads the hook arguments and the Python frame, and decides. For a breakpoint, that means evaluating the condition, counting the hit, and either publishing a stop or resuming silently. Conditions and log messages use microscope's evaluator over the stopped frame, so they behave the same as native ones.

The hook can be a function in a tiny C-ABI library that the agent loads with ctypes. The library has no libpython dependency, so one build serves every version and both GIL modes, and it is a no-op when no debugger is attached. Or it can be a tkill(SIGTRAP) that microscope recognizes by its sender and the agent's frame. Open question Q2 chooses; the library is recommended.

Values, expressions, views, and visualizers

The object model

A value is located by its object address. Its type is the type object at ob_type, and its type identity is that type's module and qualified name: tp_name for static types, or __module__ and ht_qualname for heap types. Presentation goes by type:

  • int is shown exactly at any size, printed from its digits. Arithmetic takes ints up to 128 bits, the range of microscope's exact integers. Beyond that it fails with a typed error that says so (R7).
  • float is an f64. bool and None are themselves.
  • str is text, decoded by kind. bytes is bytes.
  • list, tuple are sequences. dict is a map in insertion order. set, frozenset are sets in table order.
  • Instances show their attributes from inline values, the instance dict, and __slots__ descriptors.
  • Functions, code, and modules show their names. A cell shows its contents.

Everything else is shown as its type and address, with its __dict__ where one exists.

Every read is charged to the inspection budget. A malformed object, such as a length beyond capacity, a type that is not a type, or a cycle, ends with a problem and the raw address. It is never treated as an empty container.

The built-in types are presented by Rust code in the runtime model, called from built_in() beside the existing Go-pointer, sum-type, tuple, and coroutine presenters (R8). Paging list elements and dict entries uses the existing ViewChildren.bound slot, with the presenter's state downcast as views' state is today. The views policy allows native views only with a stated reason. The reason here is that these layouts change with every minor version and come from the target's own offsets table, which a view file cannot express without exposing per-version offsets to users. Everything above the built-ins is views.

Expressions

There is still one expression language. In a Python frame, names bind statically: a code object's local, cell, and free variable names are static facts, followed by globals and builtins. Members, indexing, and len bind against a dynamic type, a new category in the evaluator's type model (G11). The new parts are kept small:

  • A member or index on a dynamic value plans an ordinary step whose result is again dynamic, so chains reuse Op::Step and Machine::step. d[k] reuses Op::Entry, and len reuses presented_length.
  • Only loads and the choice of comparison or arithmetic wait for run time, where the machine returns the value it read.
  • An attribute that one instance lacks is a value-level problem, not a binding error, because attributes belong to instances, not types.
  • Python values are always places, at their object's address, so members of computed values are never needed.

Arithmetic and comparison follow microscope's exact rules on Python ints, floats, and bools.

The expression language cannot run Python code: properties, __getattr__, __eq__, descriptors other than slots and plain attributes, and function calls are all off limits. Each refusal says which one it hit. d[k] finds a key by a bounded scan comparing str, bytes, int, bool, None, and tuples of those by value. It does not compute hashes, which depend on the process's randomized secret. Real Python evaluation in the target is ruled out (Decisions).

The same binding works for a PyObject * in a native frame. A C extension's locals are DWARF pointers. dynamic() gains a case for C and C++ pointers whose type is PyObject, which presents the object as a Python value when the pointer is a valid object. An explicit cast to the dynamic type lets expressions reach in, such as ((py)op).name. Today's dynamic cases all return a DWARF type. A Python object has none, so this case returns the object's address.

Views and visualizers

The view language gains python. Patterns match a type's module and qualified name, for example view python collections::deque. This needs no new pattern syntax: patterns already accept :: and ., so it needs only Language::Python and a type identity whose path is the module and whose base is the qualified name. Selection happens once per type object per stop, because Python types are only known at run time. Today's session-long view cache is keyed by TypeReference, so it gains a per-stop key for dynamic types, since a freed type object's address can be reused (G12). Binding then checks the view against the type's actual attributes, so a view that names a missing attribute is rejected with its reason, as today. Built-in views cover:

  • collections.deque, OrderedDict, defaultdict, and Counter;
  • enum.Enum members;
  • dataclasses (field order);
  • datetime, decimal.Decimal, fractions.Fraction, and pathlib.Path.

numpy.ndarray is the visualizer showcase. Its PyArrayObject layout is numpy's public C ABI: data pointer, number of dimensions, dimensions, strides, and dtype. numpy wheels carry no DWARF, so the runtime model supplies that small public struct itself, as a fixed type with a stated reason. A view presents it as a shaped sequence. The existing bitmap visualizer draws an image buffer unchanged. heatmap and line-plot draw arrays of numbers once bulk reads accept language number types (G12). The bulk-read byte limits already apply. Properties computed in Python, such as .shape, are refused like any other property. PyTorch CPU tensors and pandas frames are later and need their own proof of layout.

The BPF engine

A perf_event BPF program attaches to the sampler's existing events with PERF_EVENT_IOC_SET_BPF (G13), including each follower event in attach mode. It returns 1, so perf still writes the normal sample: registers, the copied stack, and the kernel's call chain. The native part is unwound exactly as now, through unwind_sample.

The program walks the current thread's Python frame chain. It writes the frames as a BPF_OUTPUT record into the same CPU's ring, just ahead of the sample, so Processor::ingest's existing sort pairs them with no clock join. The frames are then spliced at the sample's eval-loop activations, in the frame loop at record.rs:699-714, by the same pairing rule the debugger uses. Before anything depends on that ordering, a real-kernel conformance test pins it, as dev/profiling.md requires.

  • The thread's state comes from a tid → PyThreadState map that userspace maintains from the interpreter's thread list, checked in BPF against native_thread_id. This avoids TLS discovery, which OpenTelemetry does by disassembling _PyThreadState_GetCurrent.
  • Per frame, it emits a 32-byte py_frame: the code pointer, the instruction offset, the owner, and the first line and qualified-name pointer that prove the code object's identity (Data layout).
  • Userspace symbolizes code objects through the process's CodeTable. A proof that fails means the object was freed and its address reused, and gives a frame marked as no longer readable.
  • Offsets reach BPF as a per-process py_layout map value, filled from PythonLayout on the mapping path before the process's first sample. A sample that arrives earlier says its Python frames are unknown; it does not silently lack them.
  • Frame count is bounded. A stack cut short at the bound says so. A frame that bpf_probe_read_user cannot read, because it is paged out, ends the stack as a counted truncation.
  • The walker is one __noinline global function, so the verifier checks it once. It lives in python.bpf.h, shared with the syscall programs (Syscalls).

Snapshot and live engines

The snapshot engine is the existing stopped snapshotter, iterating threads instead of tasks, as thread_pointers already does. Each thread's debugger backtrace is mixed once P1 lands, so snapshots get Python frames for free. Each thread is stored as a task row with the noun "thread", plus wait rows that gain WaitFrame::Interpreted. That keeps snapshots in their own unit with no new table. Today each snapshot builds a debugger and attaches, which limits the rate. That cost is measured and recorded before Python makes snapshots common.

The live engine is the existing live snapshotter. It reads through LiveStop, which already implements RuntimeStop, so the Python model runs on it unchanged. G3 makes it detect runtimes in every module, not only the executable, and removes its silent fallback to a stopped snapshot. It does not use 3.15's last_profiled_frame cache: that works by the profiler writing into the target, and profiling keeps the target read-only. Instead it caches code objects and rereads whole frames. It proves completeness with base_frame on 3.15, and with owner, type, and chain checks before that. A sample that fails is a counted loss, never a shorter stack.

What analysis gains

  • Looks. Python, mixed, and native, beside the existing native and logical async looks. The Python look is a python() transform modeled on logical(), which already cuts by code role: it drops Interpreter-role frames and joins the segments. Call trees, costs, diffs, pprof, and folded output need no change, because Keys::new already keys any frame by its lines.
  • GIL lanes. Sampled holds_gil and gil_requested (3.15; the GIL holder before that) per thread, recorded as label spans (gil=held, gil=waiting), so the existing label queries and density lanes draw them. Recording "GIL wait" as the cause of an off-CPU interval needs a stack or cause field that OffCpu lacks. It waits for a separate capture change, and then only where the symbols prove it.
  • asyncio tasks. The BPF record carries the thread's running task (asyncio_running_task, 3.14+). That feeds the existing claim(), which attributes a sample to a task only when the snapshots on both sides agree, as for Go and tokio today.
  • GC. 3.15's collecting flag and frame mark samples taken during garbage collection.
  • Capture. Revision 9 adds FrameKind::Interpreted. The frame row's layout is unchanged: its address is the string key of the file, qualified name, and line, its module is none, and it is symbolized once at record time, like an awaited frame. Each one records its declaring file and first line, so that two functions with the same name in different files never merge. Deferred symbolization already skips frames that are not native, which is right here: code objects die with the process.

Perf maps

Independently of Python, the sampler learns to read /tmp/perf-PID.map (G14). An anonymous executable range covered by a map becomes a pseudo-module. Its unwind information gives one rule, frame pointer kept, so both the CFI walk and the call-chain splice continue through it. It has no build ID to prove identity, so it is symbolized at record time and never deferred. The map is append-only and written while it is read, so it is reread only when a sample lands in an anonymous executable range it does not yet cover. This fixes F7 for python -X perf users, and it is the first piece Node and the JVM need.

Instrumented profiling

The probes ring is already language-neutral, but its sites are static records in an ELF section. Python names zones at run time. The probes ABI therefore gains run-time sites (R12). They work as follows:

  • The control block's reserved bytes at offset 56 point to an append-only registry of site records in target memory: kind, name, file, and line. Each record has a key in a key space of its own, apart from the i32 offsets that static sites use.
  • The collector rereads the registry when a record names a key it has not seen, and applies prefix selection as each site is defined.
  • The ABI becomes 2, and the decoder accepts 1 and 2, so existing binaries keep working.
  • The Rust, C, and Zig SDKs, the decoder, the fixtures, and the format tests change together, as the profiling page requires. JavaScript and Java SDKs will need the same thing.
  • The microscope package (sdk/python): with microscope.zone("load"):, the @microscope.zone decorator, plot, message, and label. It wraps a cdylib built from sdk/rust-probes with C exports, which also holds the agent's hook. That library carries its own control section, so the recorder discovers it when it is loaded, with no change to discovery. It is the one native component for every Python version and GIL mode. It is safe with no recorder, as the SDK contract already requires.
  • Automatic function timing is deferred. Timing every call of chosen modules without code changes would need the agent registered under the profiler tool ID. That is code injected for profiling, which the decision on targets rules out. If it returns, it will be as an explicit, separately named opt-in. A program that wants it today can call microscope.trace_calls(prefix) from the package itself. That is the program's own choice, not an injection.
  • Opting in. The recorder turns sites on by writing to the control block the SDK puts in the program. That is the existing probes contract, and a Python program enters it only by importing the package. microscope never writes to a Python program that did not.
  • Zones and samples together. Zones land in the same capture as the samples, on one clock, so the timeline shows both.

System call analysis

  • ptrace engine. At each syscall stop the thread is stopped, so its Python stack is exact. This engine has its own tracer thread and never uses the debugger's controller, so it reaches the Python model through Stacks, which both engines already share and which already owns each process's images. Stacks gains the Python walk over a memory reader: live reads for ptrace, the BPF-collected frames for BPF. The frames join the native stack in CallStack, which grows an interpreted-frame field.
  • BPF engine. When stacks are on, sys_enter runs the shared Python walker, so a trace of a Django request shows the openat made at settings.py:42. Budgets drop Python frames along with stacks.
  • Catchpoints. Catchpoints stop with mixed stacks, and $path, $arg0, and the rest are unchanged.
  • Filtering. Filtering calls by a Python frame predicate is later. It needs the walker in the filter path, so it waits until the stack path is measured.

Testing

The testing plan was reviewed separately. The review inventoried the methods the repository already uses, and it studied how py-spy, pystack, Austin, the OpenTelemetry profiler, CPython, debugpy, Delve, LLDB, and rr test the same kind of code. It also researched the evidence on what each testing method buys and costs, and priced the interpreter matrix against the pinned nixpkgs. The goal is a suite where a failure almost always means a real bug, and which costs little to keep.

Six rules get there:

  1. Every test has an oracle that is not microscope. The best oracle is the target's own account of itself. A fixture prints what CPython knows about its threads, frames, and values at a synchronization point. Then microscope stops the process and must agree. A test whose expected output came from microscope's own earlier run proves only that nothing changed.
  2. One source of truth per fact, produced at run time. Live tests check in no expected output. Expectations come from the fixture's TRUTH lines and from source markers, so nothing rots when a line moves or an interpreter changes. This is the rule that keeps the suite cheap.
  3. Assert the public result, not the machinery. Tests compare presented frames (function, file, line) and presented values, through Scenario. They do not check internal records, offsets, or the order of reads, so the reader can be rewritten without touching tests.
  4. A matrix dimension must change a layout or a build behavior. Each scenario family runs on the interpreters where its subject differs, never on the full product (matrix).
  5. No retries, no sleeps, no silent skips. These are already the repository's rules: nextest has no retries, and fixtures synchronize on observable state. A missing interpreter fails the test. An unsupported state is asserted by its typed reason. py-spy's retried CI steps and Austin's --ignore-errors show how retries and swallowed errors stop CI from catching regressions.
  6. Every oracle proves it can fail. The existing Go harness has the_truth_fails_on_the_lies_it_looks_for, and the simulator has sabotage tests. Python's harness gets the same: a test feeds it a dropped frame, a wrong line, a swapped thread, and a wrong value, and requires each comparison to fail.

Four methods were considered and left out on purpose:

  • Golden snapshots of output. Truth lines replace them. The only output files are a few short CLI and DAP mapping cases, as today.
  • A checked-in core-dump corpus for matrix builds. OpenTelemetry's corpus works, but it needs cloud storage and a bulk "rebase" command that can approve regressions unseen. Here, cores are generated when fixtures are built, as build-test-programs.sh already does with gcore, and the fixture's truth is saved beside each core. A stored core is kept only for a field bug on a build outside the matrix, together with its truth.
  • CPython's own remote unwinder as a second reader. _remote_debugging reads the same offsets the same way, so it shares microscope's blind spots on layout. It also needs ptrace rights over a process microscope already traces. In-process truth is stronger and simpler.
  • Statistical tolerance on frame content. Sampling tests may assert how often a function appears, but every sampled stack that contains it must match the truth exactly.

The truth harness

tests/go/truth.rs already parses TRUTH\t<checkpoint>\t<path>\t<kind>\t<value> lines, and the tokio suite uses the same format. It moves to tests/support/truth.rs, shared by Go, tokio, and Python, with its self-test intact. On the Python side there is one small, stdlib-only module, tests/fixtures/python/truth.py:

  • checkpoint(name) prints, for every thread: the native thread ID, each frame's qualified name, file, line, and instruction offset, and the selected locals in a canonical text. Then it prints READY and parks the calling thread.
  • Parking. Worker threads park on a threading.Event at a source marker before the checkpoint, so every stack is frozen while it is printed and while it is read. The printing thread's own frames are reported as such and left out of comparisons.
  • Canonical values. Ints in decimal, at any size. Floats as their shortest round-trip repr. Strings and bytes escaped. Dicts in insertion order. Sets sorted for cross-version comparison. Instances as their type plus their attributes. Each form is the same text the presenter must produce, defined once in the harness.
  • Code tables. At start the fixture prints each of its functions' co_lines(). Every line microscope reports for that code must appear in that table, which gives a static check with no race.
  • Steps and exceptions. Expected stepping sequences and raise sites are written as markers in the fixture source (# step 2, # raises), found by the existing source_line helper. No test holds a line number.
  • Startup. Fixtures run with -I, so the environment and the user's site-packages cannot change them. A missing interpreter fails with the variable it expected.

How an entry is obtained and run. No entry runs another operating system. There is no container and no virtual machine.

  • nixpkgs entries are ordinary flake packages.
  • A distribution entry is that distribution's own build of the CPython it ships, taken from its binary packages: for Debian, the interpreter, its stdlib packages, and the few shared libraries they need, such as glibc, zlib, expat, and libffi. Each .deb is fetched with fetchurl by hash and unpacked into the store, the way ubuntuGlibc already unpacks Ubuntu's glibc. Then patchelf points the interpreter at that distribution's own loader and libraries, as build-test-programs.sh already does for the Ubuntu glibc fixtures. Only the ELF headers change. The code, the data, and .PyRuntime are the distribution's bytes.
  • A python-build-standalone entry is a relocatable tarball, fetched by hash and pointed at the flake's glibc in the same way.

The kernel is the host's; everything above it is the build under test. Running through an explicit loader (ld.so python3.13) was rejected, because the process's executable would then be the loader, which no real deployment looks like. Within a minor version the layout never changes, so a distribution entry is never updated to follow security releases. Debian entries use snapshot.debian.org URLs and Ubuntu entries use Launchpad's, so they stay fetchable after the archive moves on.

The matrix review changed four things in the earlier plan:

  • 3.15.0 final comes from python-build-standalone. Overriding the nixpkgs source would compile CPython locally on every bump, and nixpkgs selects its patches by version, so they may not apply to final. An earlier draft planned that override.
  • Distribution binaries need their stdlib. A -minimal package alone cannot run the fixtures. The stdlib packages of the same build are fetched beside it, and PYTHONHOME points at them.   • DWARF comes from nixpkgs' debug outputs. They are 27 MiB each. python-build-standalone's 42 MB debug-full builds are not needed.
  • Fedora's build leaves the matrix. It confirmed F6 during research, but it adds nothing the entries above do not cover.

Layout conformance

  • Generated constants. layouts.gen.rs follows table.gen.rs exactly. A test regenerates it from the flake's interpreters by compiling offsetof programs against each one's headers. It fails when the checked-in file is stale, and rewrites it under MICROSCOPE_UPDATE_CPYTHON=1. The file joins the generated-files table in dev/index.md.
  • The target's own table. For each 3.13+ interpreter, a test compares every value its _Py_DebugOffsets reports against the schema microscope reads it by, and every struct size against the headers.
  • DWARF. Where a debug output exists, a third test checks both against DWARF (R3).
  • Assumptions. The owner numbers, stack-reference tag bits, str kind shift, and thread-local bytecode index are each checked against the headers by name, so a new version that moves one fails here, not in a stack.
  • Refusals. A pure test hands the provider a table with the next minor version, and a prerelease that differs from its listed one, and requires Unsupported naming the version found.

Agent tests

CPython's test_monitoring.py gives a checklist of the cases where sys.monitoring is subtle. Each case becomes a debugger scenario, whose oracle is the fixture's markers:

  • DISABLE and restart;
  • events that cannot be disabled (RAISE, PY_UNWIND, PY_THROW);
  • generators resumed, thrown into, and closed;
  • implicit and explicit re-raise, try/finally, except*, and async for;
  • a tool ID already taken;
  • a callback that fails.

Around them sit the lifecycle cases:

  • injection under thread churn;
  • a blocked main thread;
  • remote debugging disabled;
  • detach with breakpoints armed, after which the fixture prints sys.monitoring.get_tool for every ID and must match its state before attach;
  • a fork child;
  • a target that exits during injection.

Each waits for the agent's ready trap, never for time.

Simulator, BPF, and fuzzing

  • Simulator. CPython cannot run in it (R11). The Python model's reading is tested purely, through RuntimeStop over synthesized memory. The agent protocol is simulated with a golden C program that plays the agent: it fills a mailbox, calls the hook, and waits for the writes that arm it. So the hook's stop-or-continue decision, the controller's writes, and all-stop are swept by just sim. A sabotage test makes the golden agent lie about its frame and requires an oracle to catch it. The Python frame record is modeled in sim/tracing.rs, or stated there as unmodeled.
  • BPF. The walker's exactness is tested through the syscall engine, not the sampler. The truth fixture parks a thread inside a known system call at a marker, and the BPF stack's Python frames must equal its truth. That is deterministic, which a sample is not. Sampler tests then check only the pairing of frames with samples and the ring order, which a real-kernel conformance test pins first. The py_layout map value is checked against its Rust mirror through BTF, as records.h is today.
  • Fuzzing. Four new targets: section parsing and validation, line-table decoding, the object model over arbitrary memory, and the BPF frame record. Seeds come from memory the truth scenarios read, so the fuzzer starts from real layouts.

Two lessons shape the Python work now:

  • Stack integration needs both mechanisms from the start. CPython mostly needs activation splicing, and JIT runtimes mostly need PC-to-code mapping, but each runtime needs both: V8 and HotSpot have interpreters, and CPython has trampolines and a JIT. G4 makes splicing ask the model for a segment by code role, and G14 makes JIT ranges pseudo-modules. Neither knows about CPython.

The neutral pieces are the stop reasons, typed unavailability, and the groundwork hooks and plans, and the transports stay per runtime until a second one exists.

Open questions

The four large decisions are in Decisions. These remain, each with a recommendation.

Q1

How do 3.12 and 3.13 get Python breakpoints?

Both have sys.monitoring, so the agent itself works, but neither can be told to run it. The options:

  • Launch-only bootstrap (recommended). When microscope launches a 3.12 or 3.13 program, it puts a directory first on PYTHONPATH holding a sitecustomize that loads the agent dormant and then imports the program's own sitecustomize, if it has one. The agent registers no tool until microscope asks. Attach and exec into an already-running 3.12 or 3.13 interpreter report breakpoints as unavailable, with the reason. The cost is a changed environment, which child processes inherit.
  • Read-only on 3.12 and 3.13. No bootstrap. Native breakpoints, stacks, values, profiling, and syscalls only.
  • A native injection of microscope's own. Make a thread run code at a stop without the PEP 768 handler. microscope has no inferior calls, and building them for this is a large, risky change. Not recommended.
Q2

How does the agent trap?

Recommended: a tiny C-ABI hook library loaded with ctypes. It reuses the runtime-hook machinery, and it is harmless if microscope dies. The alternative is tkill(SIGTRAP), which needs no file but kills a target that raises it without a tracer, so it would need a liveness check on each event.

Q3

Free-threaded builds from the first phase?

Recommended: yes, for reading. The experiment showed the differences are small but easy to get wrong, and adding them later would mean auditing every read again.

Q4

Distribution builds in the matrix?

Recommended, and drafted into the matrix: yes. The matrix adds Debian trixie's 3.13, Ubuntu noble's 3.12, and python-build-standalone's 3.15.0, each fetched by hash, for about 80 MB. They are the static, stripped, and LTO builds that most servers and uv users run, and nixpkgs builds none of them. If the cost is unwelcome, the two distribution entries can go. They test only the loader paths, which python-build-standalone partly covers.

Q5

Contribute upstream?

Recommended: yes. Propose adding the dict-keys layout, inline values, tp_members, and the str state layout to _Py_DebugOffsets for 3.16. Each one moves a generated constant into the target's own description.

Q6

Python SDK packaging?

Recommended: a pure-Python package over the shared C-ABI library, published as a wheel per platform, so one artifact serves every Python version. A CPython extension for faster zones can follow if probe-cost shows the ctypes call matters.

Q7

A capability report per runtime?

Recommended: not yet. microscope has no per-runtime report today. Python's unavailable features first appear as typed errors where they are used: a pending breakpoint with its reason, a task-page gap, or a refused step. If users can't tell why something is off, a RuntimeReport request, extending the existing unbound-runtime reasons, follows as its own change.
