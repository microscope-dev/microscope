Following the program the user meant

Most programs are not started by naming their executable. A Node developer runs npm start, npx, node --test, or a #! script; a Python developer runs a pyenv shim, multiprocessing, or a test runner that spawns workers. In every one of these the user's code runs in a process microscope did not launch, after one or more execs, and today microscope either refuses, stops at the exec, or lets that process run untraced without saying so. This plan makes microscope follow the process tree to the code the user meant: it launches scripts, follows an exec into a different program, and debugs the children a program starts, in every client. It is general lifecycle work, not specific to Node, and it is the groundwork item G8 of the Node.js plan.

Summary

The user names the command they always run. microscope npm -- start, microscope ./cli.js, microscope node -- --test test/*.test.js, and microscope python3 -- train.py with a worker pool all reach the user's code, with breakpoints set before run armed in every process that runs it before its first instruction. Processes that only pass control along, such as sh, env, and a version manager's shim, are followed silently and never shown as something to debug.

Three pieces, smallest first.

  1. An exec into a different program keeps the same session. The new program becomes the session's main module under fresh ids, through the path that already loads shared libraries at run time, and pending breakpoints resolve in it. This alone covers env node, bash -c, and shims.
  2. A #! script is launched as the kernel runs it: microscope reads the interpreter line, loads the interpreter's image, and lets the kernel's exec chain reach the real program through piece 1.
  3. A process group. One tracer thread hosts one controller per debugged process, with one waiter whose statuses are routed by thread group. A fork child, or a watched process that execs into a program worth debugging, changes owner on that thread without ever being detached. Clients present the group as a numbered list of processes, as gdb presents inferiors.

Why a group, and why one thread. Today one OS process can run one tracing session, because each controller's waiter calls waitpid(-1) (F1), and a launched program dies with the thread that launched it (F2). Switching the session to a child would kill or lose npm, the test runner, and the watcher, and would miss every later child. Several controllers on one thread keep every process traced by the same task, so a fork child is already traced by it when it appears, and handing it to its own controller is a table update (F7, F9).

The public model stays as it is. A Debugger is still one process and all-stop. The group is a new layer above it that creates debuggers and reports which processes joined and left. Each member's DebuggerHandle works exactly as a single session's does.

Testing stays real and fast. Every case is a C fixture driven through Scenario in milliseconds, with the kernel as the oracle: /proc state, exit codes, and the fixtures' own reports. Controller orderings the kernel will not produce on demand are scripted on the fake edge. The simulator gains one small extension, for watched processes that fork and exit; it does not learn exec or vfork (F14).

The decisions that most change the work are in Decisions. Five questions were decided on 22 October 2026, in Questions; DAP hosts the group in one adapter from the start (Q4). The experiments are throwaway: a 120-line watch-only tracer in C, a hand-over probe, and a routing probe. Their results are recorded in Findings.

Scripts, shells, and shims

$ microscope bash -- -c "node app.js"
$ microscope python -- app.py                 a pyenv shim that execs python3.12

None of these forks, so each is one process. microscope follows its execs to the last program and prints one line for each, such as process 6001 executed /usr/bin/node. It stops at an exec only when asked (catch exec), as gdb does. stop_at_entry stops at the entry of the final program, not of env.

In VS Code and the browser

Each member is a session in VS Code's Call Stack view, nested under the process that started it, served by the one adapter that hosts the whole group. In the browser, a process switcher beside the stop banner lists the members, their state, and how each joined. The followForks setting becomes follow, with followForks: true meaning follow: "all".

Findings

From reading the controller, clients, and simulator, and from experiments on this machine (kernel 7.2, Fedora glibc 2.43) with nixpkgs' Node 26.5.0, npm, and the pinned CPython 3.14.

F1

One tracing session per OS process

Each controller's waiter polls waitpid(-1, __WALL | WNOHANG) (native.rs, spawn_waiter), so two controllers would take each other's statuses. A global lease (SessionLease::acquire, LINUX_SESSION_ACTIVE) refuses a second with “another Linux tracing session is already active in this process”. Tests are safe only because nextest runs each in its own process, and DAP's fork children work only because each runs in its own adapter process. Only the simulator drives several controllers in one process, through handle_message.

F2

A launched program dies with its controller thread

trace_child sets PR_SET_PDEATHSIG(SIGKILL), which fires when the launching thread exits. A design that ends the parent's controller to start the child's would kill npm, the test runner, or the watcher. The tracer thread must live as long as the group.

F3

The main program is pinned in about 60 places, and library loading is the template

The controller keeps executable, executable_identity, c_library, module_image, and unwind_info for the session, and about 15 sites use ModuleId::new(0) for the main module. Stepping, awaits, and target descriptions read self.module_image directly. The handle copies one Arc<ModuleImage> into every clone, and 31 client lines use it. Shared libraries already load at run time: the loader breakpoint queues a refresh, new modules get fresh ids and ModuleLoaded, unloaded ones ModuleUnloaded, and reresolve_breakpoints places pending specs. The web's image cache is keyed by ModuleId and never cleared on unload, so reusing id 0 for a new program would serve the old image.

F4

npm runs whichever node is first on PATH

npm run by a copy of node outside PATH started the app with the node on PATH; with none on PATH, the app failed with “node: command not found”. npm exports npm_node_execpath as its own node, but the script does not use it. So a follow filter cannot be “the same executable as the parent”; it has to recognize a runtime, or a program the user names.

F5

Watching a process tree costs nothing measurable

A tracer that sees only fork, vfork, clone, exec, and exit events, and resumes every stop at once, ran node --test over 20 files in 105–112 ms against 104–116 ms untraced, interleaved, five runs each. It took 330 stops: 20 forks, 21 execs, and 125 thread creations. Watching intermediate processes is therefore free, and the plan keeps every descendant traced until it exits or is let go.

F6

The common chains, as the kernel reports them

  • npm start: node forks, the child execs bash (as sh), which execs node in the same process. Three execs, one fork.
  • node --test, --watch: node forks, the child execs node.
  • Python subprocess and spawn pools: vfork, then exec. Four vforks for one subprocess.run and a two-worker spawn pool.
  • libuv forks with a plain fork; CPython with vfork.

A filter decided at fork time sees npm's child as node and then loses it to sh; it must be decided at each exec.

F7

A process handed over at its exec runs nothing first

The watch tracer stopped npm's final node at its exec event, sent SIGSTOP, and detached it. /proc showed it stopped with no tracer, at the loader's entry (rip 0x7ffff7fe3d40, in ld-linux). A second tracer seized it, interrupted, sent SIGCONT, saw the interrupt stop and then the SIGCONT at the same address, suppressed it, and the app ran and printed normally. Inside one tracer thread no hand-over is needed at all, and DAP hosts every member in one adapter (Q4), so this probe is recorded only as the fallback that design does not need.

F8

The kernel runs every script form; microscope need not parse them

#!/usr/bin/env node, #!/usr/bin/env -S node --no-warnings, an absolute interpreter, and a script whose interpreter is another script all ran correctly under the tracer: one exec to env then one to node, or one exec straight to node. The arguments node saw were the script path followed by the user's. So microscope launches the script itself, and needs the interpreter line only to load the first image.

F9

Every status can be routed to its owner

A routing probe tracked which thread groups it knew. Over three node --test runs of 20 files and one Python pool run, no new process stopped before its parent's fork event was seen. About 80 new threads per run stopped before their CLONE event, but every one's thread group (/proc/PID/status Tgid) was already known. The controller already parks such early stops (unowned_stops); the router does the same one level up, keyed by thread group, and parks a process whose parent event has not arrived.

F10

vfork children may be held under followForks today

From reading only: settle_vfork_windows sends the vfork child through track_fork_child, and scrub_and_settle holds any child while a receiver is open. plans/forks.md says vfork children stay untraced. If held, the parent waits blocked in vfork for up to two minutes of adoption timeouts, and the child's session plants traps in memory the parent shares. Phase G0 reproduces this first.

F11

The CLI cannot print while the user types

The CLI reads a line, sends it, and waits; events are gathered only while a request is in flight (execute_until_stop). rustyline 18's ExternalPrinter is unused. A batch run maps any completed script to exit 0, whatever the inferior did. The web pushes state from a pump task and can already show asynchronous changes, but holds one Debugger (src/web/session.rs).

F12

Names that find a Node process

Attach by name matches /proc/PID/comm or the first argument's file name, as pgrep -x does. Node 26 names its main thread node-MainThread and Node 24 MainThread. A program that sets process.title, as npm does, rewrites both its command name and its whole command line to the title. Otherwise a script's name appears only as a later argument.

F13

Node's inspector reaches children through NODE_OPTIONS

NODE_OPTIONS reaches every node a tree starts: with --inspect=127.0.0.1:0 in it, node --test over three files started three inspectors, one per file, each on its own port, and npm start two, npm's and the app's. But a flag there is the wrong carrier. Any --inspect flag forces node --test to one file at a time, and --inspect-wait hangs every node nobody connects to. The banner of a child is not microscope's to read: node --test swallowed it. The Node plan's F29–F31 replace both: a preload in NODE_OPTIONS that waits only in a process microscope traces, and the address read from memory. Sending SIGUSR1 before Node installs its handler killed node on 22, 24, and 26 (exit 138). The handler appeared in SigCgt 12–14 ms after exec.

F14

The simulator models fork, not exec or vfork

The simulated kernel has fork, clone, exit, job-control holding, and several tracers, but no execve or vfork; plans/simulator.md puts both out of scope. Fork holding's simulator work was 1,667 added lines. Modeling exec and vfork would cost about 2,000–3,000 lines to exercise exec handling that already runs on the real kernel. A watched-process extension, on fork, clone, exit, tgkill, and detach only, needs no new kernel rule.

F15

Python's agent leaves forked children

The agent disables itself in a forked child (os.register_at_fork). On 3.14 a member's controller can install it again by remote attach. On 3.12 and 3.13 it arrives only through the launch bootstrap, which clears its variables for children, so followed children on those versions have no Python breakpoints unless the bootstrap is told to stay.

F16

A runtime is often in a library, not the executable

The nixpkgs CPython 3.12 and 3.14 executables list libpython3.x.so as NEEDED and hold no _PyRuntime. Debian's node is a 400 KB executable whose V8 is in libnode.so.137. At the exec stop only the executable and the loader are mapped, so runtime detection there would watch every one of these programs instead of debugging it.

F17

Node's inspector, verified for children

The Node plan's F29–F31 were run on official 22, 24, and 26, nixpkgs 22, 24, and 26, and Debian's libnode 24. A preload that opens the inspector and waits only when TracerPid matches microscope's tracer held every traced node before its first line. That covered each file's process under node --test and both nodes of a node → sh -c → node chain. Each was released in 6–34 ms, with the test files still run concurrently. A breakpoint on GetTargetIds gave each process's inspector address with nothing printed or listed.

  • Controllers are unchanged in kind. Each owns one process, its stops, sites, plans, and StopIds, and is driven through handle_message, as the simulator already drives several in one process.
  • Watched processes are not controllers. They have no image, breakpoints, or stops; the tracer resumes every stop at once, delivering signals unchanged, and re-evaluates the policy at each exec.
  • Ownership moves on the thread. A process changes between watched and debugged, or from a parent's controller to its own, without leaving the tracer, so it never runs untraced and never takes an extra signal.
  • The lease stays. It now covers the tracer thread; a second group in the same process is refused as a second session is today.

Exec into a different program

This is the first piece and stands alone: it fixes env, shells, and shims for single-process programs before the group exists.

Main program state. The controller's executable, executable_identity, c_library, module_image, and unwind_info move into one MainProgram with its ModuleId. The constant ModuleId::new(0) sites read self.main.id, and LoadedModule::main takes the id. launch_path and the debug-file search stay with the session. This is a refactor with no behavior change, committed alone.

At an exec, handle_exec_event already clears sites, plans, agents, watchpoints, and libraries. When the new image is not the current program, the controller now:

  1. Reads /proc/PID/exe through a new native operation (path, inode, bytes) and loads it with the existing module loader, with load_program's architecture check, under fresh ids. The image cache keyed by inode means a node that execs node loads once.
  2. Drops the old main's Image breakpoint locations, as drop_library_locations does for libraries; they belong to the old image and are never rebased. A breakpoint by address becomes pending with the reason “set by address in /usr/bin/env”, and is never planted in the new program.
  3. Unregisters the old main (ModuleUnloaded), registers the new (ModuleLoaded), evicts the old image's runtime cache entry, and sends DebuggerEvent::ProgramChanged { previous, program }.
  4. Runs the existing load_main_image and refresh_libraries, whose reresolve_breakpoints places breakpoints by function, by line, and by runtime in the new program and its libraries.
  5. Resumes, unless catch exec is set, in which case it stops with StopReason::Exec { program }.

An image that cannot be read (deleted, memfd, another architecture) keeps today's visible state for that process: Exec { followed: false } with the reason, and later requests refused with it.

Loading off the tracer thread. A new program's debug information can take seconds. The process stays stopped at its exec; the load runs on the existing worker pool, and the controller marks itself loading and serves requests meanwhile, answering image-based ones with “loading /usr/bin/node”. This matters once one thread serves several controllers.

The handle. DebuggerHandle holds the main image in a watch channel the controller writes before it sends ProgramChanged, so clients still receive immutable values. module_image() returns an owned Arc. executable() becomes the current program; launched() is what the user named, which DAP's runInTerminal must launch. LoadedModuleSnapshot gains main: bool, so clients stop recognizing the main module by path.

Pending native breakpoints. The CLI and web refuse a native breakpoint the current program cannot resolve, unless it is Python's. With exec following, break uv_run before env execs node must be accepted as pending, with a notice, as DAP already does.

Scripts

Program::load today fails on any file that is not ELF. A file that begins with #! is handled as the kernel does: the interpreter path is the first word after #!, with no PATH search, and an interpreter that is itself a script is followed up to the kernel's limit of four. microscope loads the final ELF interpreter's image as the program and keeps the script as launch_path, which it executes. The kernel's initial exec maps that interpreter, so the launch's initial stop works unchanged, and an env that execs node is the exec of the previous section. Arguments are the script's, untouched; env -S and interpreter options work because microscope never builds the command line itself (F8).

A script whose interpreter line names a missing file fails before launch with that name: error: ./cli.js names /usr/local/bin/node, which does not exist. Until the exec piece lands, a script fails with error: ./cli.js runs /usr/bin/env, which execs another program; launch that program itself instead of “not an ELF file”.

The process group

The tracer thread

Today spawn_controller starts one OS thread per controller. The group starts one tracer thread that owns the waiter and a table of members, and runs a loop over three inputs: requests addressed to a member, wait statuses, and transfer messages from controllers. A single session is a group of one, so every client keeps its present path until it opts into more.

Routing. The router maps every traced thread to its thread group and every thread group to a member or a watched process. A status for an unknown thread is routed by its Tgid; one for an unknown process is parked until a fork, vfork, or clone event names it, and handed over with it, which is what controllers already do for early thread stops (F9). A parked status with no owner after its process exits is reaped and dropped.

Blocking calls. A controller that blocks in waitpid on one of its own threads stalls the whole group. The calls that do (wait_status in attach rollback and orphan settling, reap, poll_status) are audited: each either becomes a parked wait the router completes or keeps a bounded wait that is documented as such. An assertion in debug builds measures any call longer than 50 ms on the tracer thread.

Joining

  • A fork child starts traced by the tracer thread, because ptrace attaches it to the tracing task automatically. Its parent's controller scrubs the traps it inherited, as it does today, and sends Transfer { pid, start_time, program } to the group instead of holding or releasing it. The policy decides: a new controller adopts it at its first stop with the parent's program, already loaded, and the group's breakpoints planted before it resumes; or it becomes watched.
  • A vfork child shares its parent's memory until it execs. It is always watched during the vfork window, with the parent's traps lifted as today, and decided at its exec, which ends the window. It never becomes a member with sites in shared memory.
  • A watched process that execs is decided again. Promoted, it gets a controller whose first stop is that exec stop, with ExpectedStop::AdoptedExec, the path launch_by_exec already uses, so its program loads and its breakpoints are planted before the new image's first instruction.
  • A member that execs follows the new program in place (Exec) when the policy still wants it, or drops its sites and becomes watched when it does not, with a line saying so.
  • Threads of a member stay its controller's, as today.

Leaving and ending

  • A member that exits is reaped by its controller, reported as MemberExited, and stays in the list as exited until the user clears it, so a test file's result can be read after it ends.
  • A watched process stays traced until it exits, because it may still exec into a program the policy wants, and watching it costs nothing (F5). follow = "none" releases children at fork, exactly as today.
  • Shutdown kills every process descended from a launched root, members and watched alike, and detaches attached ones, restoring their bytes. The tracer thread lives until the last process is reaped or released, so PR_SET_PDEATHSIG never fires early (F2).
  • Detaching one member detaches its process and leaves the rest of the group running.

Follow policy

A process is decided when it joins and again at each exec, from its settled program: the image the exec loaded, the libraries it needs, its arguments, and how it relates to the launched root. The executable alone is not enough, because CPython and Debian's Node keep their runtimes in a library (F16). A process whose executable decides it is decided at the exec stop. A dynamically linked process that is not decided there stays watched. It gets one internal trap at the loader's _dl_debug_state, and is decided at the first loader stop after its NEEDED libraries have loaded, still before main. A process that is promoted there gets its controller at that stop, with the group's breakpoints planted before it resumes. One that stays watched has the trap removed, so a watched process holds no planted byte after that stop. The extra stop per exec is unmeasured; its budget is under 1 ms (Performance).

Runtime detection uses the same probes that bind a runtime model, over the executable and its loaded libraries. It reads only their symbol tables, through the image cache, so libc is read once for the whole tree. A program microscope cannot load is never debugged and is reported once. The CLI takes --follow, the config file a [follow] table, and DAP a follow property; DAP's followForks: true means all.

Attaching follows children the attached process starts after the attach; processes it started before are not adopted. An attached process's environment is not microscope's, so its node children have no preload. Such a child is signalled with SIGUSR1 only once SigCgt shows Node's handler, and until then has read-only JavaScript, with the reason (F13).

Stops across processes

Each member is all-stop within itself, and publishes its stop only once all its threads are stopped, as now. The group adds one rule: when a member publishes a stop, the group pauses every other running member and reports GroupStopped once they have stopped. continue resumes every member; a step resumes only the stepping member's process, and the others stay stopped until the step ends, as threads of one process do under a step today.

Pauses that cross a stop are the hard case. Two members can hit breakpoints at once: the group reports the first to publish and keeps the second's stop pending, presented at the next continue without resuming, exactly as a second thread's breakpoint hit is kept today. A member that is pausing when it exits is reported as exited. Watched processes are never paused: they hold no user state, and pausing them could stall a pipe the members wait on.

Interrupts and runtimes. Ctrl-C interrupts the selected member as a single session does, which for Node first tries Debugger.pause. Once that member's stop is published, the other members are paused natively. The Node plan's rule that no CDP request is made at a published stop then holds for the whole group: a member paused natively shows its JavaScript frames with unnamed stack locals, as any native stop does (Node plan F11). Python members follow the same rule for their agent.

Profiling and system calls. A recording or a syscall trace of a group covers every member. Each member binds V8's or CPython's layout and walker state for its own process, and binds again after each exec. Each sample and each call stays with its process and program, so npm start shows the app's JavaScript, not npm's.

Stopping a member while its siblings run is the alternative, offered as [follow] stop = "process" (Q1). It suits servers with independent workers, and needs the CLI's asynchronous notices, which the group requires anyway.

Clients

CLI. A selected member, shown in the prompt when the group has more than one: (microscope [2]). New commands: processes lists members with state and how they joined; process N selects one; detach process N. Every existing command acts on the selected member, and breakpoint commands on the group. Joins, exits, and releases that happen while the user is at the prompt print through rustyline's ExternalPrinter, above the prompt line. run and continue wait for a group stop or the whole group's exit. A batch run exits non-zero when a process the policy wanted could not be followed, and with the root's status otherwise; a fixed-string -e transcript is the test.

Web. The session's single target becomes a group. A process switcher sits beside the stop banner, and every panel's state is keyed by member. Joins and exits arrive through the existing pump, and the console shares the CLI's commands.

DAP. One adapter hosts the whole group (Q4). The parent adapter owns the tracer thread and every member. For each member that joins, it sends startDebugging with a configuration naming the member and the parent adapter's socket. VS Code's descriptor factory in editors/vscode and nvim-dap's adapter function connect that child session back to the same adapter, which serves it from the member's DebuggerHandle. No process is detached or re-attached, so Yama's ptrace_scope 1, the SIGSTOP hand-over, and the adoption timeouts all go away.

This replaces followForks' separate-adapter path from plans/forks.md; followForks: true becomes follow: "all". A client that cannot start child sessions, or cannot route them back, gets one console line per member saying it is debugged but not shown, and follow can be set to none. Once no client uses it, the held-child API (hold_forks, attach_held, release_held) and its simulator model are retired in a follow-up, which F7's probe would otherwise have served as a fallback.

Messages. Each client says when a process is not followed, with its command and the reason, once per process. Nothing the program starts disappears silently in any client.

Node and Python in a group

Node's inspector. A member that joins at an exec cannot be given an inspector by SIGUSR1, which kills a process that has not installed Node's handler yet (F13). The launch environment instead carries the Node plan's preload in NODE_OPTIONS, after any value the user set, and MICROSCOPE_TRACER naming the tracer thread. Every node the tree starts runs the preload. In a process the tracer traces, member or watched, it opens the inspector and waits; elsewhere it does nothing. follow = "none" releases children at fork, so they are untraced and never wait.

The group connects to every node that waits. A member's controller arms the group's JavaScript breakpoints and then releases it. A watched node is released at once, in 6–34 ms (F17). No inspector flag is added, so node --test keeps its concurrency, and its runner, which has no inspector, runs on. Each member's address comes from its own GetTargetIds breakpoint and is never printed or listed. A program that gives its children a clean environment loses the preload; those members have read-only JavaScript, with the reason.

Python's agent. On 3.14 a member gets the agent by remote attach, as attach does today. On 3.12 and 3.13 the launch bootstrap is changed to keep its variables for children when the group follows them, so a spawned worker loads it too, and to stay inert in processes microscope does not debug (Q5).

Go. Go's os/exec forks with a clone that behaves like vfork; it is handled as vfork is.

The exec, script, and group scenarios run in just and should add under 5 s at 16 threads; Node and Python end-to-end tests run in just all. Questions and decisions

Each question below was decided on 22 October 2026. Each card marks its decision in bold, with the reasoning beside it.

Q1

Group stop or process stop by default?

Decided, as recommended: group stop, so everything the user debugs together is frozen while they read it, as threads are. stop = "process" serves servers whose workers must keep answering.

Q2

Should npm's own node be a member?

Under auto it is, because it runs a runtime microscope models. Decided, as recommended: yes, and say so in its join line. Excluding it would need a rule about npm specifically, and native breakpoints in node legitimately hit there. --follow-skip npm-cli.js could exclude by script if users ask.

Q3

Stop at every exec?

Decided, as recommended: no: print a line and continue, with catch exec to stop. A chain like env then node would otherwise stop twice before the program starts.

Q4

One DAP adapter for the group, or one per member?

Decided: one adapter from the start, against the recommendation to ship per-member adapters first. The per-member step would have extended followForks' hand-over to execs, only to be replaced. Going straight to one adapter removes Yama's ptrace_scope limit, the SIGSTOP hand-over, and the adoption timeouts in G4, at the cost of editor-side routing in VS Code's descriptor factory and nvim-dap's adapter function before DAP follows anything new. G5 then retires the held-child API.

Q5

Python 3.12 and 3.13 children?

Decided, as recommended: keep the bootstrap's variables for children when following, so spawned workers load the agent; forked children re-enable it after fork. The alternative is native-only debugging of those children, with the reason.
